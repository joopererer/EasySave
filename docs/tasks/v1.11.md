### 真机回退现象（build 34）

1. 每次重启 App 后，首页“最近保存”和历史页的缩略图加载都很慢。
2. 部分帖子打开大图后一直加载不出来，底部缩略图条要很久才出现一两张；视频和
   Live 帖子一直转圈。
3. 从大图浏览返回历史页时，原本已显示的缩略图消失，很久才重新加载；上下滚动
   列表时也会这样。

### 原因

- 问题 1 和问题 2 的改动把封面和大图都改成读取**原图的全部字节**
  （`AssetEntity` 原始数据），再用 `ResizeImage` 解码到屏幕尺寸。`ResizeImage`
  只按缩小比例解码，并不会少读文件字节：手机上每个封面都要读取十几 MB 的原图
  并解码，非常慢。
- 每张按屏幕尺寸解码后约 6 MB（1080×1439×4）。几十个封面很快超出 Flutter
  图片缓存上限（默认约为可用内存的一个固定比例），触发频繁驱逐与重新加载，
  于是返回列表或滚动时缩略图消失、反复重载。
- 视频与 Live 帖子共用同一条取图路径，通路被挤占后缩略图条迟迟不出现，表现为
  一直转圈。
- 主题判断错误：封面根本不需要原图，系统缩略图（MediaStore）已经足够；
  “屏幕尺寸”应当由**系统按缩小比例解码**实现，而不是“读原图字节再缩小解码”。

### 教训

- **测试与基准必须覆盖真实场景**。主机测试和基准只测了“单张大图”的解码耗时
  和内存，没有覆盖“一次加载几十张封面”的并发与缓存压力，也没有反映手机的
  CPU、内存与 I/O 速度，因此基准数字（屏幕尺寸解码快 1.7×、省内存 22.9×）
  看似正确，却掩盖了“多读十几 MB 字节 × 几十张”的真实成本。
- **解码尺寸优化不等于取字节优化**。`ResizeImage` / `cacheWidth` 只影响解码
  后的位图大小，不影响读取与传输的字节数；对本地原始文件，代价主要在前者之外。
- **不要为“更清晰”牺牲列表的可用性**。封面是列表的一部分，宁可只用系统
  缩略图；清晰度留给点开大图之后。
- **回退要彻底**。撤回时连带删除新文件与新增测试，相关文件与 build 33 逐字节
  一致，避免留下半启用的路径（`progressive_asset_image.dart`、`decodeTargetFor`、
  放大层、字节预算等都不可残留）。

### v1.11 重新实现的方向

1. **封面和网格缩略图只使用系统缩略图（MediaStore），不读取原图字节。** 继续
   使用 `photo_manager` 的 `thumbnailData` / `AssetEntityImageProvider`（非
   original）路径；占位与淡入如果要做，只在这一层之上做，不改变取图来源。
2. **大图按屏幕尺寸取图走 Android 原生解码。**
   - API 29+：`ContentResolver.loadThumbnail(uri, Size)`，由系统按缩小比例解码，
     不把原图读入 Dart 内存。
   - API 28 及以下：`BitmapFactory.Options.inSampleSize`。
   - 通过原生通道返回**解码后的图像或纹理**（例如 `ImageReader`/`Bitmap` 转
     `Surface` 纹理，或 `ui.decodeImageFromPixels` 的 RGBA 字节），通道里不要
     传原图文件字节。
3. **放大时再按需加载原图细节**，可考虑 `BitmapRegionDecoder` 分块：按
   (mediaId, level, tileX, tileY) 做瓦片缓存并设字节上限，配合现有手势变换。
4. **性能验证必须包含真实场景，且在真机上记录**：
   - “一次加载 50 个封面”——记录首屏完成时间、缓存驱逐次数、峰值内存。
   - “快速滑动 20 张大图”——记录每张到位时间、峰值内存、是否出现空白帧。
   - 真机上用 `adb shell dumpsys meminfo com.james.easysave` 前后对比
     （不使用 `run-as`，不读取 App 私有目录），并把耗时与内存写入交接记录。
   - 主机测试只能作为回归保护，不能作为性能结论。

## 待讨论方向（尚未决定）

### 标签

- 标签写入文件 XMP 标准关键词字段 `dc:subject`；层级标签使用 `lr:hierarchicalSubject`，使标签随文件流转，并让 File Organizer、OnlineAlbumPlugin 等读取同一字段，不依赖 App 间接口同步。
- EasySave 内部另建标签表用于筛选；标签库默认为空，提供引导及导入/导出，格式与 OnlineAlbumPlugin 统一。
- 考虑在 provenance-spec 增加“用户标签使用标准字段，不进入 prov 命名空间”一节。

### Pinterest 支持

- 下载优先从 `i.pinimg.com` 的 `originals` 尺寸取原图；可参考 gallery-dl、yt-dlp 的 Pinterest 支持思路，注意 gallery-dl 为 GPL，仅借鉴思路并审查许可证。
- Pinterest 内容大量为转存，来源需同时记录帖子地址及帖子指向的原始链接（如有）；评估是否为规范增加字段。
- 项目分工：UniPost 负责通过官方 API/OAuth 发布并接收 EasySave 一键交接；UniSearch 负责反查高清版本或原始出处；n8n 负责自动化（如收藏到指定画板后下载并打标签）；OnlineAlbumPlugin 负责电脑浏览器采集。
- 合规方向：通过官方 API 读取用户自己的画板与收藏，产品定位以“保存自己收藏的内容”为主。

### 长视频（超过 3 分钟）

- 手机端显示文件大小；超过阈值时仅 Wi-Fi 自动下载，移动网络下排队，允许手动强制下载（已有记录，合并到此）。
- “交给电脑下载”：手机仅将链接与来源信息放入 Google Drive 任务队列，由电脑端浏览器扩展或桌面程序取出并下载；复用 Tessera-system 的 Drive `appDataFolder` 收件箱思路。
- 不采用服务器代为下载到云盘：Google Drive 不会自行抓取网址，服务器方案带来成本、隐私及登录 Cookie 风险。
- 建议纳入 v2.0 Drive 同步设计，与文件及历史同步共用同一套 Drive 访问与授权。
