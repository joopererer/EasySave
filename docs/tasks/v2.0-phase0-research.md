## 1. 评估背景与核心约束

在 EasySave v1.12 的大文件断点续传演进中，团队总结了极为关键的五条底层教训（见 `HANDOFF.md` §6.1）：
1. **保护性阻塞条件必须有真机耗时数据**；
2. **续传起点只能取磁盘上临时文件的实际物理长度**（严禁信任内存进度或“只增不减”假设）；
3. **暂停后继续必须恢复同一个原生任务**（保持同一 taskId，避免开启新轮次导致旧文件被删）；
4. **续传测试必须覆盖首轮任务**；
5. **严禁在插件/第三方库之上叠加自己的双重状态机**（避免并发竞态与死锁）。

进入 v2.0 阶段，架构的核心目标是用自研的**统一后台传输服务**（Unified Background Transfer Service）替换现有的 `background_downloader` 插件及 App 层的断点续传补丁代码。该服务必须统一下列两大业务场景：
1. **媒体下载（Download）**：单文件/多文件下载、大文件断点续传、前台服务保活、通知聚合；
2. **云同步上传（Upload - Google Drive）**：分块断点续传（Resumable Upload）、统一调度并发度与网络状态。

因此，对底层开源组件的技术评估，核心关注**架构对称性（下载+上传共用调度）**、**严格安全拦截（重定向逐跳域名校验与 Cookie 剥离）**以及**能否在不堆叠补丁的前提下天然契合设计规范**。

## 2. 评估基准：阶段 0 · 七条规则

依据 [`v2.0-design.md`](v2.0-design.md)「阶段 0：统一后台传输服务」章节定义，评估的唯一硬性准绳为以下七条规则原文（架构本身保证，不靠补丁）：

1. **一个文件只有一个写入者**：写入前对 .part 加文件锁，拿不到锁就不写。
2. **断点只看磁盘**：续传起点 = .part 的实际长度，没有第二份「续传记录」。
3. **所有事件串行处理**：用户指令、网络变化、失败、定时重试、重启恢复都进同一个队列，由调度器逐个处理。
4. **暂停、断网、被杀是同一件事**：停掉写入，.part 留着；继续只有一种做法。
5. **网络变化不打断正在进行的传输**，只在恢复时叫醒调度器。
6. **只有一个归属方**：服务是唯一的驱动者，没有「接管」和「交接」。
7. **只有用户操作能丢弃已下载数据**（取消、删除），或服务器证明文件已变（200、校验值或总大小不符）。

### 候选一：OkHttp（square/okhttp -> lysine-dev/okhttp）

* **仓库名称**：`square/okhttp`（主开发仓库已迁移至 [lysine-dev/okhttp](https://github.com/lysine-dev/okhttp)）
* **仓库地址**：[https://github.com/lysine-dev/okhttp](https://github.com/lysine-dev/okhttp)（原链接 [https://github.com/square/okhttp](https://github.com/square/okhttp) 保持自动重定向）
* **许可证（LICENSE 文件）**：**Apache-2.0**（依据仓库根目录 [LICENSE.txt](https://github.com/lysine-dev/okhttp/blob/main/LICENSE.txt)）
* **最近一次发布日期**：**2026-10-22**（标签 [parent-5.5.1](https://github.com/square/okhttp/releases/tag/parent-5.5.1)；5.x 系列最新发布版本为 **5.5.1**，Maven 坐标为 `com.squareup.okhttp3:okhttp:5.5.1`）
* **最近一年提交数（2025-11-23 至 2026-11-23）**：**≥100**（GitHub API 单页 100 满额，极度活跃，见 [commits/main](https://github.com/lysine-dev/okhttp/commits/main)）
* **体积**：`okhttp` 核心 AAR 约 800KB–1.2MB（包含 Okio 依赖），无额外原生动态库。

#### 能否满足七条规则（逐条判定，相比旧版分析重新核对）
1. **规则 1（一个文件只有一个写入者：加文件锁）**：**需改造/需自行实现**。*(相比旧版判定无变化)* OkHttp 仅负责网络传输与流式读写，不感知本地文件系统，写入前对 `.part` 的文件锁（FileLock）必须由上层 Worker / TransferService 实现。
2. **规则 2（断点只看磁盘：起点 = .part 实际长度，无第二份记录）**：**需改造/需自行实现**。*(相比旧版判定无变化)* OkHttp 支持在 Request Header 传入任意 `Range: bytes={part.length()}-`，可直接由上层读取物理文件长度注入。
3. **规则 3（所有事件串行处理：单队列调度器）**：**需改造/需自行实现**。*【标出变化：原判定为“同任务恢复需改造”，现按设计文档规则 3 判定】* OkHttp 内部的 `Dispatcher` 是并发连接分发器，不是状态机事件串行队列；所有用户指令、网络恢复、重试事件必须由上层基于 Kotlin 协程单线程 actor/Channel 调度器串行处理。
4. **规则 4（暂停、断网、被杀是同一件事：停写入，留 .part，继续只有一种做法）**：**需改造/需自行实现**。*【标出变化：原判定为“统一调度满足”，现按设计文档规则 4 判定】* OkHttp 的 `Call.cancel()` 仅关闭网络流，不会删除磁盘文件；上层必须保证在取消时不触碰 `.part` 文件，恢复时统一通过调度器重新发起包含断点 Range 的 Call。
5. **规则 5（网络变化不打断正在进行的传输，只在恢复时叫醒调度器）**：**满足 / 需上层配合**。*【标出变化：原判定为“前台服务需改造”，现按设计文档规则 5 判定】* OkHttp 底层 Socket 不会因 Android 系统网络广播而主动切断连接；上层网络监听器（ConnectivityManager）只需在检测到网络恢复时向调度器发送唤醒事件。
6. **规则 6（只有一个归属方：服务是唯一驱动者，无接管和交接）**：**满足 / 需上层实现**。*【标出变化：原判定为“请求策略满足”，现按设计文档规则 6 判定】* OkHttp 仅作为 Worker 的 HTTP 客户端，不持有全局状态，生命周期完全由单一的 TransferService 驱动。
7. **规则 7（只有用户操作或服务端证明改变才丢弃数据）**：**需改造/需自行实现**。*【标出变化：原判定为“自愈需改造”，现按设计文档规则 7 判定】* OkHttp 本身不会丢弃数据，但需上层在收到 HTTP 200、校验值或总大小不符时执行 `.part` 的清空（truncate 0）。

* **能否接入我们的请求策略**：**完全满足**。OkHttp 拥有工业级的 `Interceptor` 机制和 `followRedirects(false)` 开关，是业内唯一能百分之百在 HTTP 30x 重定向发包前逐跳拦截、检查 `Location` 域名白名单、清洗 Header 与剥离 Cookie 的组件。
* **前台服务与进程重启后的恢复方式**：由上层应用自建 `TransferService`（前台服务），并依托 SQLite（`transfer.db`）持久化未完成任务，重启后扫描磁盘恢复。
* **结论**：**推荐方案：作为底层唯一网络传输引擎，在其上自研统一后台传输服务**。

* **仓库名称**：`tonyofrancis/Fetch`
* **仓库地址**：[https://github.com/tonyofrancis/Fetch](https://github.com/tonyofrancis/Fetch)
* **许可证（LICENSE 文件）**：**Apache-2.0**（依据仓库根目录 [LICENSE](https://github.com/tonyofrancis/Fetch/blob/v3.0x/LICENSE)）

* **最近一年提交数（2025-11-23 至 2026-11-23）**：**0**（自 2024-12-03 提交后已停止日常更新，项目处于非活跃/维护停滞状态，见 [commits/v3.0x](https://github.com/tonyofrancis/Fetch/commits/v3.0x)；2024 年内提交数为 41 次）
* **体积**：`fetch2` + `fetch2core` 全套约 1.2MB–1.8MB（包含 Room、RxJava 扩展等）。

#### 能否满足七条规则（逐条判定，相比旧版分析重新核对）
1. **规则 1（一个文件只有一个写入者：加文件锁）**：**不满足 / 需改造**。*【标出变化：原判定为“满足（队列去重）”，现按设计文档规则 1 判定】* Fetch 仅依靠内部内存队列 Task ID 去重，并未在操作系统层面对物理临时文件（`.fetch` / `.part`）加排他性文件锁（FileLock），无法防止跨进程或多实例的并发写入。
2. **规则 2（断点只看磁盘：起点 = .part 实际长度，无第二份记录）**：**不满足 / 严重冲突**。Fetch 强依赖 Room 数据库中的 `downloaded` 字段作为第二份续传记录；当进程被杀或异常退出时，若磁盘实际落盘与数据库不同步，会导致断点错乱甚至文件截断。
3. **规则 3（所有事件串行处理：单队列调度器）**：**不满足**。*【标出变化：原判定为“部分满足”，现按设计文档规则 3 判定】* Fetch 的用户指令、网络监听与数据库状态更新在不同线程池异步处理，不具备单线程 actor 的全局串行保证。
4. **规则 4（暂停、断网、被杀是同一件事：停写入，留 .part，继续只有一种做法）**：**不满足**。*【标出变化：原判定为“不满足（无上传）”，现按设计文档规则 4 判定】* Fetch 内部区分了 `PAUSED`、`FAILED`、`CANCELLED` 多个状态分支，且在某些失败重试场景下会主动清理分片临时文件。
5. **规则 5（网络变化不打断正在进行的传输，只在恢复时叫醒调度器）**：**不满足**。*【标出变化：原判定为“满足（前台服务）”，现按设计文档规则 5 判定】* Fetch 内置网络监听器，一旦监听到网络断开或切换，会在内部直接打断正在传输的连接。
6. **规则 6（只有一个归属方：服务是唯一驱动者，无接管和交接）**：**满足**。Fetch 自建独立服务，为单一驱动者。
7. **规则 7（只有用户操作或服务端证明改变才丢弃数据）**：**不满足**。Fetch 在不可恢复异常或分片校验错误时会自动清除已下载分片。

* **能否接入我们的请求策略**：**不能直接接入**。Fetch 默认使用 `HttpUrlConnectionDownloader`，内部循环自动跟随重定向，未暴露逐跳域名白名单校验与 Cookie 剥离钩子。
* **前台服务与进程重启后的恢复方式**：自建后台服务与 NotificationManager，进程重启后自动查询 Room 数据库恢复。
* **结论**：**参考设计（参考其优先级调度结构，但不直接集成）**。维护停滞，且内部存在第二份续传记录，违背规则 2 与规则 5。

4. **规则 4（暂停、断网、被杀是同一件事）**：**需改造**。分段文件管理复杂，暂停与网络中断的处理分支不统一。
5. **规则 5（网络变化不打断传输）**：**需改造**。网络变化时存在主动重连分段逻辑。
6. **规则 6（唯一归属方）**：**满足**。内置标准的 Android `DownloadService` 前台服务。
7. **规则 7（数据丢弃限制）**：**部分满足**。

* **能否接入我们的请求策略**：**不能接入**。底层基于 JDK Transport（`HttpURLConnection`），未集成 OkHttp Interceptor 体系，无法在跳转前实施域名白名单与 Cookie 剥离。
* **前台服务与进程重启后的恢复方式**：自建 `DownloadService` 前台服务 + Room 数据库恢复。
* **结论**：**参考设计（参考其 DownloadService 与 Mutex 结构，不用）**。专注于多连接/BT 下载，且无法接入请求策略。

## 6. EasySave 既有工程与依赖深度分析（重点）

针对 EasySave 仓库当前代码与 Gradle 构建脚本进行只读实测分析：

### 6.1 EasySave 当前对 OkHttp 的依赖判定
* **结论**：**EasySave 当前对 OkHttp 既无直接依赖，也无间接依赖**。
* **Gradle 依赖树真实证据**：
  在 `app/android` 模块下执行 `./gradlew app:dependencies --configuration releaseRuntimeClasspath` 检查发布运行时依赖树，**完全不存在 `com.squareup.okhttp3:okhttp`**。依赖树中与 square 相关的仅有一项由 Datastore 间接引入的 `okio`：
  ```text
  +--- androidx.datastore:datastore-core-okio:1.1.7
  |    \--- androidx.datastore:datastore-core-okio-jvm:1.1.7
  |         +--- com.squareup.okio:okio:3.4.0
  |         |    \--- com.squareup.okio:okio-jvm:3.4.0
  ```
  在 `app/android/app/build.gradle.kts` 中亦未声明任何 okhttp 依赖。
* **工程落地要求**：阶段 0 引入 OkHttp 时，必须在 `app/android/app/build.gradle.kts` 中添加**直接依赖**：
  ```kotlin
  dependencies {
      implementation("com.squareup.okhttp3:okhttp:5.5.1")
  }
  ```

### 6.2 现有 MediaPolicyRedirects.kt、NativeMediaRequest.kt 技术栈分析
1. **`MediaPolicyRedirects.kt`（位于 `app/vendor/background_downloader/...`）**：
   * **技术栈**：**完全不基于 OkHttp**。它是一个纯 Kotlin 对象（`object MediaPolicyRedirects`），不包含任何网络请求代码，只依赖标准库与 `kotlinx.serialization.json`。
   * **复用可行性**：**传输服务可以直接 100% 复用其策略逻辑**。其定义的 `HostRule` 解析、`reject(raw, rules)` 域名匹配、`rejectHeaders(headers, host)` 头部过滤以及 `isPermittedIfRange` 正则，可直接作为 OkHttp 拦截器的规则决策核心。
2. **`NativeMediaRequest.kt`（位于 `app/android/app/.../com/james/easysave/`）**：
   * **技术栈**：**不基于 OkHttp，而是基于 JDK 原生的 `java.net.HttpURLConnection`**（见其 L8、L117 `val connection = URL(current).openConnection() as HttpURLConnection`）。通过设置 `connection.instanceFollowRedirects = false` 并以 `for (hop in 0..5)` 手动循环处理 30x 重定向。
   * **复用可行性**：**传输服务不能直接复用其网络执行体**。但其逐跳校验（`checkedUri`、`checkedHeaders`、`deny`）和安全剥离逻辑，可以直接改造并下沉为标准的 OkHttp `Interceptor`。

## 7. 与设计文档的差异

本节仅列出本次开源调研与实际代码依赖核查中发现的、[`v2.0-design.md`](v2.0-design.md) 中尚未写到或需补充的新事实：

### 差异 1：Android 15 dataSync 前台服务 24 小时内最多运行 6 小时限制
* **出处**：Android 官方行为变更规范文档 [Behavior changes: Apps targeting Android 15 or higher -> Foreground services](https://developer.android.com/about/versions/15/changes/foreground-services#datasync)。
* **新事实**：
  - 设计文档第 64 行与「待决定问题」第 3 项仅提示“新系统对 dataSync 有运行时长限制，上线前要核实”。
  - 调研核实查明：在 Android 15（API 35）及以上设备上，`dataSync` 类型前台服务在 **24 小时内累计运行时间上限为 6 小时**（time limit of 6 hours within a 24-hour period）。
  - 当达到 6 小时上限时，系统会触发 `Service.onTimeout(int, int)` 回调。服务**必须在回调内调用 `stopSelf()` 停止自身**；若超时未停止，系统将抛出 `ForegroundServiceDidNotStopInTimeException` 并导致应用崩溃。
  - **对架构的影响**：`TransferService` 必须重写 `onTimeout` 回调，在超时前平滑暂停 Worker 并持久化 `.part` 进度，等待用户重新激活或次日配额恢复；大文件后台批量下载需具备分批调度意识。

### 差异 2：Android 15 禁止从 `BOOT_COMPLETED` 广播启动 dataSync 前台服务
* **出处**：Android 官方规范文档 [Restrictions on BOOT_COMPLETED broadcast receivers starting foreground services](https://developer.android.com/about/versions/15/changes/foreground-services#boot-completed)。
* **新事实**：
  - 设计文档组件表中规划了由 `Store` 负责“进程重启后恢复”。
  - 调研核实查明：Android 15 严禁在 `BOOT_COMPLETED` 广播接收器中直接调用 `startForegroundService()` 启动 `dataSync` 类型前台服务，违者系统直接抛出 `ForegroundServiceStartNotAllowedException`。
  - **对架构的影响**：开机自愈不能依赖接收 `BOOT_COMPLETED` 广播直接拉起 `TransferService`。必须通过 WorkManager 的 `OneTimeWorkRequest` 触发合规的后台任务，或者推迟到用户下次点击打开 App（Activity 处于前台）时再由前台唤醒恢复未完成传输。

### 差异 3：OkHttp 仓库迁移至 lysine-dev 与版本选择
* **出处**：GitHub 官方仓库 [square/okhttp](https://github.com/square/okhttp) 与 [lysine-dev/okhttp](https://github.com/lysine-dev/okhttp)。
* **新事实**：
  - 设计文档第 66 行只写了 Worker 使用 “OkHttp”，未提及版本与仓库变更。
  - 调研核实查明：OkHttp 的主分支维护组织已从 Square 迁移到 `lysine-dev/okhttp`（square 组织地址做重定向）；其 Maven 发布坐标仍保持 `com.squareup.okhttp3:okhttp` 不变。
  - 5.x 系列已有成熟发布（最新标签为 `parent-5.5.1`，发布于 2026-10-22），工程选型应直接选用 5.x 稳定版本 **5.5.1**（`com.squareup.okhttp3:okhttp:5.5.1`），而非停留在旧的 4.x。

### 差异 4：EasySave 当前工程未依赖 OkHttp
* **出处**：`app/android/app/build.gradle.kts` 及 Gradle `app:dependencies --configuration releaseRuntimeClasspath` 实测输出。
* **新事实**：
  - 设计文档假定可在 Kotlin 层直接用 OkHttp 编写 Worker。
  - 调研核实查明：EasySave 当前既无直接依赖也无间接依赖 OkHttp，现有网络模块（`NativeMediaRequest.kt`）使用 `HttpURLConnection`。阶段 0 开工需在 `app/android/app/build.gradle.kts` 中显式添加直接依赖 `implementation("com.squareup.okhttp3:okhttp:5.5.1")`。

### 差异 5：Ketch 仓库缺失根目录独立 LICENSE 文件
* **出处**：GitHub API `repos/khushpanchal/Ketch/license` 查询（返回 404，SPDX 为 null）。
* **新事实**：
  - 设计文档在「首轮候选」表中列出了 Ketch。
  - 调研核实查明：Ketch 根目录下未包含独立 LICENSE 文件，仅在 README 末尾声明。存在开源合规与法务审计风险，不可作为直接引入的第三方依赖。
