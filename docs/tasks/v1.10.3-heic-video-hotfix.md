## 1. 结论先说：两点必须先知道的局限

1. **8 个 HEIC 样本不在工作区。** 本轮无法在此机器上给出真实 API 31 的解码结果表。
   仓库里没有任何样本文件（`git status --untracked-files=all` 为空，本机也无
   `Downloads` 里的样本）。因此交付的是**能产出该表的装置**，而不是伪造的表：
   - Robolectric 侧的 `HeicSampleDecodeTableTest`（把样本放进
     `app/android/app/src/test/resources/fixtures/heic/` 即打印逐样本一行）；
   - 真机只读自检 `HeicSelfCheck`（见第 6 节）。
   这两条的**回答都不是“真机结果”**：Robolectric 的 `BitmapFactory` 是影子
   实现，对任何输入都返回一张假 bitmap，因此模拟环境的表会一律显示
   `decodable=true`。这一点在该测试的文档注释里也写明了。
2. **`media_request_policy_test.dart` 在本机无法通过**，与本次改动无关：该测试
   用 `Process.run('node.exe', …)` 调
   `extension/scripts/export_request_policy_fixtures.js`，而这台机器没有安装
   Node（`node -v` / `Get-Command node.exe` 均失败）。因此 `npx vitest`（扩展
   侧测试）同样无法运行。基线 tag 上该测试同样是失败的。

## 2. 问题 1 的推断验证（能验证的部分）

### 2.1 已验证：CDN 侧 `format/jpg` 与 `format/jpeg` 等价，且需要 `/q/100`

用 `spec/fixtures/xhs/xhs_multi.expected.json` 里的真实 token，对线上 CDN 做了
只读 GET（2026-11-12）：

| 请求 | 字节 | Content-Type | 像素 | SHA-256 前 16 |
| --- | --- | --- | --- | --- |
| `sns-img-bd.xhscdn.com/{token}` | 1,007,645 | octet-stream | 1290×1608 | `ea80472824226ac8` |
| `sns-img-bd…/{token}?imageView2/format/jpg` | 245,672 | image/jpeg | 1290×1608 | `3c9c08f36ae0f5e4` |
| `sns-img-bd…/{token}?imageView2/format/jpeg` | 245,672 | octet-stream | 1290×1608 | `3c9c08f36ae0f5e4` |
| `sns-img-bd…/{token}?imageView2/format/jpg/q/100` | 1,030,648 | image/jpeg | 1290×1608 | `2ed25b20f19ff3ab` |
| `sns-img-bd…/{token}?imageView2/format/webp` | 226,092 | — (RIFF/WEBP) | — | — |
| `ci.xiaohongshu.com/{token}` | 1,007,645 | octet-stream | 1290×1608 | `ea80472824226ac8` |
| `ci…/{token}?imageView2/format/jpg` | 245,672 | — | 1290×1608 | `3c9c08f36ae0f5e4` |
| `ci…/{token}?imageView2/format/jpg/quality/100` | 245,672 | — | 1290×1608 | `3c9c08f36ae0f5e4` |

结论：

* `format/jpeg` 与 `format/jpg` **完全一致**（同 SHA-256），parser 用 `jpg` 没有
  问题，不需要为写法差异改 parser。
* `format/webp`、`format/png` 都被执行（返回 WEBP / PNG），说明 `imageView2`
  在 `sns-img-bd` 与 `ci` 两个 host 上都被真实执行，不是被忽略的查询串。
* **但** `format/jpg` 会重编码：1290×1608 不变，体积从 1,007,645 降到 245,672
  （约 -76%）。这与 NEORUAA/XHS_Downloader_Android 的
  `?imageView2/format/jpeg` 是同一行为 —— 它拿到的是“服务器转码的 JPEG”，
  而不是原始字节。
* `/q/100` 被接受（`/quality/100` 不被接受），体积回到 1,030,648，接近原始
  1,007,645。因此本轮新增的派生候选用 `imageView2/format/jpg/q/100`。

### 2.2 未验证：带 alpha 的 HEIC 在本机平台解码器上的真实结果

需要真机执行（第 6 节）。本轮只把**判定逻辑**做成可测、可复现的形式，并把
“不可解码 → 不接受该候选”接到下载链路上。

### 2.3 关于“HEIC 原图优先”的推断

推断（平台解码器不支持带 alpha 的 HEIC）与已观察到的现象一致，但本轮**没有**
在真机上证实。为避免用猜测改行为，代码采取的是“先问设备能不能解码”：能解码
则照旧接受 HEIC 原图，不能解码才拒绝。

## 3. 改动

### 3.1 新增：本机解码自检（原生）

* `app/android/app/src/main/kotlin/com/james/easysave/ImageDecodeProbe.kt`
  - `sampleSizeFor` / `decide`：纯函数判定表（无 Android 依赖，可单测）。
  - `probeFile` / `probeUri`：先用 `BitmapFactory`（`inJustDecodeBounds` 取边界，
    再按 `inSampleSize` 采样到长边 ≤256px 解码）；失败且 API ≥28 时再用
    `ImageDecoder`（`setTargetSampleSize`）。任一解码器能出像素即视为可解码。
  - 解码线程池是 **cached**（不是 fixed）：一个卡死的解码只占自己那条线程，不会
    饿死后续探测；与 photo_manager 队列、磁盘 executor、主线程都无关。
* `MediaStoreBridge.kt`：新增 `probeImageDecodable`（仅允许 App 私有目录内的路径）、
  `probeMediaDecodable`（按 MediaStore id 只读探测）、`mediaDuration`。
  回复统一 post 回主线程。

### 3.2 新增：候选规则

* `media_content_type.dart`
  - `requiresDeviceDecode()` / `kDeviceDecodedStillExtensions`：哪些容器需要设备自检。
  - `ContentVerdict.rejectUndecodableOnDevice`。
  - `derivedJpegOriginal()` / `withDerivedJpegOriginals()`：给“原尺寸、无处理参数、
    且自身不是 jpg/png/webp/gif”的小红书图片 token 增加
    `?imageView2/format/jpg/q/100` 候选，插在该 token 之前；若 parser 已经给了同一
    host+path 的 `format/jp*` 候选则不重复添加。
* `download_manager.dart`
  - `planFiles` / `planFilesForItem` 走 `withDerivedJpegOriginals`。
  - `resourceForCandidate()`：派生候选克隆同 host+path 的已声明资源（角色、请求
    要求、cookie 域完全一致），未知 URL 仍由 policy 拒绝。
  - `_gatedVerdict()`：只对 `requiresDeviceDecode` 的成品做探测；拒绝时日志
    `result=rejected:undecodable_on_device device_probe=… device_reason=…`，然后按
    既有候选阶梯继续（最终可落到预览图并标「非原图」）。
  - 探测结果是 `unknown`（超时/无通道）时**不拒绝**，保持原行为。

### 3.3 重试与网络栈

* `download_manager.dart`
  - `kCandidateRetryBackoffs = [600ms, 1200ms, 2400ms]`，`kCandidateRetryLimit = 3`；
    `candidateRetryCount` 逐候选计数（旧快照的 `candidateRetryUsed` 以 1 读入）。
  - 日志：`retry=backoff retry_index=n/3 wait_ms=… candidate_seq=a/b`，每次尝试一行。
  - `retryCapFor`：候选数 × (1 + 3)，上限 `kAttemptHardCap = 24`。
* `transfer_headers.dart`（新）：`unifiedTransferHeaders()` 统一补
  `User-Agent`（浏览器 UA）与 `Accept-Encoding: identity`，已声明的值优先。
* `download_manager._probeContentLength`：`HEAD` → **`GET` + `Range: bytes=0-0`**，
  从 `Content-Range` 读总长（200 时退回 `Content-Length`），请求头与正式下载一致。
* `session_media_download.dart`：同一套默认头。

### 3.4 已保存的不可解码文件

* `history_db.dart`：`HistoryFile.undecodable`（`files_json` 新增
  `undecodable: 0|1`，缺失即“未检测”，不需要迁移，备份 v2 的 `BackupFile` 不含该字段）。
* `history_decode_check.dart`（新）：每次会话最多一次，后台、只读、一次一个文件，
  最多 8 个/次，逐条写回判定；日志 `[HeicProbe] step=checked rows=… undecodable=…`。
* `history_cards.dart`：卡片底部提示「本机无法显示此格式」。
* `gallery_browser.dart`：该条目改为提示页 + 「重新下载」；点击先弹二次确认
  （说明会删除相册里的旧文件），确认后走 `MediaDeleteService.deleteMedia`
  （系统删除授权）再重新下载。

### 3.5 防卡死

* `verified_asset_image.dart`：每项独立 `kLocalThumbnailTimeout = 5s` 看门狗
  （每 widget 一个 Timer，无共享闸门、不读整份原图）；超时回退到 fallback 并记
  `[ThumbLoad] event=local_decode_failed kind=thumb|original reason=timeout`，
  解码错误同样记 `reason=decode`。超时**不**把 asset 标记为 unreadable（可能只是忙）。

### 3.6 问题 2

* `live_pairs.dart`：`_samePairId` 改为“双方都有 pairId 且相等”或“同一次下载写入”
  （`savedAt` 相差 ≤ `kSameDownloadPairWindowMs = 60s`）。旧 `…_1.jpg` 与新
  `…_1.mp4` 因此不再合并为实况。
* `gallery_locator_service.dart`：新增 `assetByExactName` / `assetByBaseNameOfType`。
* `download_manager._findExistingAlbumAsset`：先全名（含扩展名），再“同基名且同类型”，
  最后才退回旧的全名映射 —— 扩展名不同的旧文件不再回答新文件的 assetId。
* `gallery_browser._initVideo`：静态图不再交给播放器（`asset.type == image` 时改走
  运动片段或网络），并对本地/网络两类失败记录 `[PreviewPlayer] event=failed
  source=… item_kind=… asset_kind=… type=…`（只有类型，无 URL）。
* `PublicMediaWriter.kt` + `MediaMetadataProbe.kt`：视频 insert 时写入
  `DURATION/WIDTH/HEIGHT`；publish 后读回 DURATION，仍为 0 时用
  `MediaScannerConnection.scanFile` 扫一次并再读回；两条日志
  `[MediaImport] event=duration_read|duration_rescan duration=… media=…`。
  保存结果 map 里也带回 `duration`。

## 4. 网络栈与请求头差异（改动前后）

| 维度 | preflight（改前） | 正式下载（改前） | 改后 |
| --- | --- | --- | --- |
| 协议栈 | `dart:io` HttpClient（`package:http`） | 原生 OkHttp（background_downloader） | 不变，但请求报文一致 |
| 方法 | `HEAD` | `GET` | preflight 也用 `GET` + `Range: bytes=0-0` |
| User-Agent | 站点声明里没有就不发 | OkHttp 默认/站点声明 | 两处都发浏览器 UA |
| Accept-Encoding | 未设置（`dart:io` 默认 gzip） | 未设置（OkHttp 默认 gzip） | 两处都 `identity` |
| Referer | 站点声明 | 站点声明 | 不变 |
| 协议版本 | HTTP/1.1（`dart:io`） | OkHttp（HTTP/2 优先） | 仍不一致：**无法在 Dart 侧统一**，见下 |
| 重试 | 无 | 插件 `retries: 0`，由 Dart 计数 | Dart 计数，reset/timeout 3 次退避 |

与 NEORUAA/XHS_Downloader_Android 的差异（只借鉴思路，未复制代码）：

| 做法 | 别家 | 我们（v1.10.3） |
| --- | --- | --- |
| 重置重试 | 同一地址最多 10 次，0.5s 起指数退避上限 15s | 同一候选 3 次，0.6/1.2/2.4s，然后换候选 |
| 断点续传 | `Range` + `If-Range`（ETag/Last-Modified） | 仍由 background_downloader 的 `resumable` 处理，本轮未改 |
| OkHttp | `retryOnConnectionFailure(true)`，HTTP/2 + HTTP/1.1 | 插件默认，本轮未改 |
| 头 | `Accept-Encoding: identity`、浏览器 UA、Referer | 已统一（本轮新增） |
| 原图 | 原始格式走 `sns-img-bd`，JPEG 走 `ci…?imageView2/format/jpeg` | 原图优先，另加 `sns-img-bd…?imageView2/format/jpg/q/100` |

未在本次统一的一项：`dart:io` 只支持 HTTP/1.1，原生是 HTTP/2 优先。要彻底一致
只能把 preflight 也搬到原生侧，属于 v1.11 范围。

## 6. 真机只读自检（产出解码结果表）

1. 用本轮 APK 的**自检构建**安装（或临时用
   `flutter build apk --release --dart-define=EASYSAVE_HEIC_SELFCHECK=true`）。
2. 把 8 个样本拷到 App 自己的外部目录下的 `heic-probe/`，即
   `/sdcard/Android/data/com.james.easysave/files/heic-probe/`
   （`adb push <样本> /sdcard/Android/data/com.james.easysave/files/heic-probe/`）。
3. 冷启动 App，然后在「我的 → 日志导出」拿到 `v16dl.log`，过滤 `HeicSelfCheck`。
   每个样本一行：
   `sample name=…_4.heic bytes=… verdict=decodable|undecodable decoder=bitmapfactory|imagedecoder reason=ok|decode_failed bounds=1536x2560`
4. 该自检**只读**：只列 `heic-probe/`，只调用 `probeImageDecodable`（原生侧会拒绝
   App 私有目录以外的任何路径），不写、不移动、不删除任何文件；样本可随时自行删掉。

普通（不带 `--dart-define`）的发布 APK 中该功能是死代码，不会运行。

## 8. 真机验证步骤（尚未验证）

准备：Xiaomi M2002J9E（Android 12）。**不要卸载 App、不要清数据、不要手动删相册文件。**

1. **HEIC 保存**：打开 `6af3c278000000001c031f21`、`6af1ad13000000003400572d` 重新下载。

     HEIC 候选出现 `device_probe=undecodable device_reason=decode_failed` 时紧跟
     `result=rejected:undecodable_on_device`，随后换候选；最终保存的是 jpg（或预览图 +

   旧的 jpg。

     `DflxolxpdHT_1.mp4` 显示 12 秒而不是 0 秒；日志有
     `[MediaImport] event=duration_read duration=12000`。
