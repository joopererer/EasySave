# EasySave v2.0 设计文档

Nov 22, 2026 · @James

## 概述

v2.0 让 EasySave 把下载的原图原视频备份到用户自己的 Google Drive，换手机可以一键恢复，并能把已备份的文件从手机上删掉以释放空间。实现前先做一件基础工作：用一个自研的统一后台传输服务替换现有下载架构，下载和上传共用它。

**目标**

- 下载稳定：断网、暂停、App 被杀、网络切换都能从断点继续，不再出现 v1.12 那类多层状态打架的问题。
- 备份：下载完成后自动（或手动）上传到 Drive，Live 图按照片 + 视频成对保存，保留来源信息。
- 恢复：新手机登录同一 Google 账号后，恢复历史记录，按需下载文件。
- 释放空间：已备份的文件可以只留在云端，手机上保留缩略图和记录。

**不做（v2.0 范围外）**

- WebDAV / S3 等自建存储（v2.1）。
- 标签与分类目录（v2.2，考虑与 OnlineAlbumPlugin 共用格式）。
- Live 图转 Motion Photo（v1.13，排在 v2.0 之后；云端始终保存原始成对文件）。
- 多设备实时双向同步。v2.0 以「一台主力手机备份、新手机恢复」为主，两台手机同时使用只保证不丢数据，不保证即时一致。
- iOS、浏览器扩展端的云端功能。

**阶段**

1. 阶段 0：统一后台传输服务，替换现有下载链路，功能对用户不变。
2. 阶段 1：Google 登录 + 上传队列（手动备份、自动备份）。
3. 阶段 2：备份清单同步 + 换机恢复。
4. 阶段 3：「仅在云端」+ 手动释放空间。
5. 阶段 4：按规则自动释放空间。

每个阶段单独发布一个版本，真机验证通过后才进入下一阶段。阶段 0 不涉及云端，可以先发布为 v1.13 之前的一个小版本，也可以作为 v2.0 的内部里程碑，见「待决定问题」。

## 背景：为什么先做统一传输服务

v1.12 的断点续传从 build 63 改到 79，共 17 个验证包，几乎每个问题都是同一类：三层各自管理状态的程序对同一件事看法不一致。云端上传要在 App 关闭时运行，也需要续传，如果建在现有结构上，这些问题会再来一遍。

| 层 | 自己管的状态 | v1.12 中由它引起的问题 |
| --- | --- | --- |
| 插件 background\_downloader + WorkManager / JobScheduler | 任务状态、内部重试、ResumeData、临时文件位置 | 失败后删除 ResumeData；内部重试不带 Range 从 0 重下；被取消的任务又跑起来；取消时删掉续传数据 |
| App 的 DownloadManager | 轮次、续传记录副本、等待网络、自动续传、结算 | 断点记录与磁盘文件不一致；两轮任务同时写一个文件；提前按 0 文件结算 |
| 两份 Flutter 程序（界面 + 悬浮球） | 各自一套 DownloadManager，靠归属与交接规则协调 | 已结算批次被接管；悬浮球进度卡住；当前轮次被当作旧轮次丢弃 |

v1.12 的做法是在 App 这层不断加规则去「纠正」插件，规则之间又产生新冲突。最后能稳定，靠的是回到几条朴素原则：断点以磁盘上的实际文件为准；一个文件只有一个写入者；暂停后恢复同一个任务。阶段 0 把这些原则变成架构本身，而不是补丁。

## 阶段 0：统一后台传输服务

用一个 Kotlin 前台服务替换 background\_downloader 和 App 层的续传逻辑：下载只由它驱动，App 界面和悬浮球都只发指令、读状态。用户看到的功能不变，这一阶段的验收标准就是 v1.12 的全部回归清单。

**七条规则（架构本身保证，不靠补丁）**

1. 一个文件只有一个写入者：写入前对 .part 加文件锁，拿不到锁就不写。
2. 断点只看磁盘：续传起点 = .part 的实际长度，没有第二份「续传记录」。
3. 所有事件串行处理：用户指令、网络变化、失败、定时重试、重启恢复都进同一个队列，由调度器逐个处理。
4. 暂停、断网、被杀是同一件事：停掉写入，.part 留着；继续只有一种做法。
5. 网络变化不打断正在进行的传输，只在恢复时叫醒调度器。
6. 只有一个归属方：服务是唯一的驱动者，没有「接管」和「交接」。
7. 只有用户操作能丢弃已下载数据（取消、删除），或服务器证明文件已变（200、校验值或总大小不符）。

**组件**

| 组件 | 职责 | 实现要点 |
| --- | --- | --- |
| TransferService | 前台服务，持有通知，进程存活的依据 | foregroundServiceType=dataSync；空闲 60 秒后自行停止 |
| Scheduler | 串行处理事件，决定状态转移和谁开始跑 | 单线程协程（actor）；并发上限：图片 3、大文件 1 |
| Worker | 执行一次 HTTP 传输，写 .part | OkHttp；每 256KB 或 1 秒上报一次进度 |
| Store | 持久化任务，进程重启后恢复 | SQLite（transfer.db），不存 cookie |
| Policy | 请求头白名单、cookie 剥离、跳转白名单 | 复用 MediaPolicyRedirects.kt、NativeMediaRequest.kt |
| Finalizer | 校验 → 写来源信息 → 写入相册 → 通知写历史 | 收尾期间任务不可取消；结果必写入 Store |
| Channel | 两份 Flutter 程序的接口 | MethodChannel 发指令，EventChannel 收状态 |

**状态机**

&#91;embedded content: 传输任务状态机 · 10 个状态\]

只有「下载 / 上传中」会写 .part；四种停下来的状态都保留已传输的数据，恢复时一律回到「排队中」，由调度器按 .part 长度续传。

**.part / .meta**

每个任务在 App 私有目录 transfers/ 下有一对文件：\<jobId>.part 存已下载的字节，\<jobId>.meta 存下列字段（JSON）。Store 是任务列表的来源，.meta 是恢复时的校验依据。

| 字段 | 用途 |
| --- | --- |
| url | 当前候选地址（地址过期时可替换） |
| total | 预期总字节，续传时与 Content-Range 总大小比对 |
| etag / lastModified | 有则通过 If-Range 发送，判断服务器文件是否变化 |
| mime / sniff | 预期类型，收尾时校验 |
| policyKey | 请求策略引用（站点、Referer 规则），不存 cookie 值 |

**续传协议**

- 起点 n = .part 长度。n > 0 时发 Range: bytes=n-，有校验值时加 If-Range。
- 206 且 Content-Range 起点 = n、总大小 = total → 追加写入。
- 200、起点不符、总大小不符 → 截断 .part 从 0 写，记 restart\_detected 和原因。
- 416 且 n = total → 已下完，直接进入收尾。
- 403 / 410 → 通知 Flutter 重新解析拿新地址；新地址总大小一致就续传，否则从 0 下。

**重试策略**（2026-11-23 修订）

- 网络类错误判定：Worker 报网络类错误时，先查 `ConnectivityManager` 当前默认网络是否具有 `NET_CAPABILITY_VALIDATED`：
  * 无可用网络（未验证或断网）：进入 `waiting_network`，不计次数；
  * 网络可用（已验证）：按「其他错误」处理，计次并按 5 / 15 / 30 / 60 / 120 秒退避重试，用完进入 `interrupted`。
  * `waiting_network` 的任务只在网络从「无可用」变为「可用且默认网络稳定 3 秒」时重新排队。初次注册时系统立即回调的 `onAvailable` 若此前并未断网，不算「恢复」。
- 其他错误 → 间隔 5 / 15 / 30 / 60 / 120 秒重试 5 次，用完进入 `interrupted`（「已中断，点继续」）。
- 空间不足 → `storage_full`，保留 .part，空间恢复或用户点继续时重新检查。

**收尾**

先沿用 v1.12 的两步（写来源信息、复制进相册），阶段 0 稳定后再改为一遍：在相册里建 IS\_PENDING 条目，从 .part 流式复制时插入来源信息。732MB 视频的收尾预计可从约 50 秒降到复制所需的 10 秒左右（以 v1.12 的 import\_copy\_ms 实测 7–11 秒为参考），是否符合来源信息规范需先评估。

**Flutter 接口**

- 指令：enqueue(批次)、pause、resume、cancel、retry、snapshot。
- 事件：状态变化、进度（每 1 秒或 1%）、收尾阶段、完成（带相册媒体编号）。
- 两份 Flutter 程序订阅同一个事件流，都不再持有自己的下载状态。历史记录由服务在完成时回调 Flutter 写入；没有 Flutter 程序在运行时，结果先留在 Store，下次启动时补写。

**TikTok 等 session 传输**

v1.12 里这类下载在 Flutter 内用 WebView cookie 完成。迁入服务后，cookie 只通过内存传给 Worker，不写入 Store 或 .meta；进程重启后需要重新解析拿 cookie 再续传。

**迁移**

1. 新服务与旧链路并存一个验证周期，由开发者选项切换；全部回归通过后改为默认。
2. 升级时仍在进行的旧任务：能从插件 ResumeData 找到临时文件的，挪为 .part 续传；找不到的从 0 下载。
3. 下一个版本移除 background\_downloader，以及轮次、接管、结算保护等 v1.12 补丁代码。

**测试**

Kotlin 单元测试用 OkHttp MockWebServer 覆盖：206 续传、200 回退、If-Range 变化、总大小不符、416、403 换地址、进程重启后从 Store 恢复、两个 Worker 抢同一个锁。真机验收见「测试与验收」。

## 阶段 1：Google Drive 登录与上传

只申请 drive.file 权限：EasySave 只能看到和改动它自己创建的文件，用户 Drive 里的其他内容它碰不到。上传走阶段 0 的传输服务，用 Drive 的可续传上传协议，断网、被杀后从服务器已收到的位置继续。

**登录与授权**

- 登录用 Android Credential Manager（Sign in with Google），Drive 权限用 Google Identity Services 的 AuthorizationClient 单独请求，只在用户打开「云端备份」时弹出。
- 没有自己的服务器，不保存 refresh token。每次上传前由服务静默调用 authorize() 取新的 access token；已授权时不弹界面，需要重新同意时任务进入「需要登录」状态并通知用户。
- 待核实：后台服务（没有 Activity）里静默 authorize() 是否可靠；OAuth 同意屏幕处于「测试」发布状态时授权是否有有效期限制。两点都在阶段 1 开工前用一个小原型验证。
- 与 OnlineAlbumPlugin 共用 Google Cloud 项目时，同意屏幕显示的是该项目的应用名称和图标，见「待决定问题」。

**Drive 上的结构**

```
EasySave/
  media/<平台>/<年份>/<postId>/   原始文件，Live 图的照片与视频并排
  posts/<postId>.json              帖子元数据
  manifest/                        备份清单（阶段 2）
```

- 文件名沿用本地导出名；每个文件的 appProperties 写 postId、itemIndex、role（photo / video / live\_still / live\_clip）、pairId、md5，恢复和去重都靠它们，不靠文件名。
- 文件内嵌的来源信息保持不动，上传的就是相册里的那一份。
- 帖子元数据包括：平台、postId、作者、标题、下载时间、文件清单。原帖链接是否写入，见「待决定问题」。

**上传流程**

1. 触发：自动备份打开时，下载完成即加入上传队列；也可以在历史页多选后手动备份。默认只在 Wi-Fi 下上传。
2. 去重：用 md5 查询 Drive 上是否已有同一文件，有则只更新记录。md5 在阶段 0 的收尾复制时顺便算出并存入历史记录，上传前不再重读文件。
3. 创建上传会话：POST uploadType=resumable，拿到会话地址，存入 Store（视为凭证，不写日志）。
4. 分块上传：每块 8MB（256KB 的整数倍），从相册条目直接读流。
5. 中断后：用 Content-Range: bytes \*/total 问服务器已收到多少，从那里继续。会话过期，或返回 404 / 410，就重新创建会话从 0 上传。
6. 完成：比对 Drive 返回的 md5Checksum 与本地 md5，一致才标记为「已备份」，写入 driveFileId。同一帖子全部文件完成后写 posts/\<postId>.json。

**界面**

- 「我的」页新增「云端备份」：登录状态、自动备份开关、仅 Wi-Fi、已备份 / 待备份数量、Drive 剩余空间。
- 历史卡片加一个小的云端状态角标：未备份不显示、上传中、已备份、仅在云端（阶段 3）。
- 下载队列分「下载」「上传」两个标签，暂停、继续、重试与下载一致。
- Drive 空间不足时暂停自动备份并提示，不重试。

## 阶段 2：备份同步与换机恢复

云端以「每个帖子一个 JSON + 它的原始文件」为准，恢复时把这些 JSON 读回来重建历史记录，文件按需下载。v2.0 只做单向：主力手机备份、新手机恢复。

**备份清单**

- 每个帖子的 posts/\<postId>.json 沿用现有本地备份（Backup schema 2）的字段，加上每个文件的 driveFileId、md5 和 updatedAt。两套备份用同一个导出函数，不分叉。
- manifest/index.json 只存汇总：帖子数、文件数、总大小、最后更新时间、schema 版本。它丢了可以从 posts/ 重建。
- 增量：帖子记录或文件状态变化时，只重写该帖子的 JSON；多次变化在 30 秒内合并为一次写入。
- 现有的本地备份文件夹功能保留，与云端备份互不影响。

**第一次打开云端备份**

已有历史记录要一次性补传（你目前约 290 个帖子、750 个文件）。开始前先显示数量和总大小、预计占用的 Drive 空间；只在 Wi-Fi 下进行，可以暂停。按下载时间从新到旧上传，最近的内容最先得到保护。

**换机恢复**

1. 新手机安装 EasySave，登录同一个 Google 账号并授权。
2. 读 manifest/index.json，显示「云端有 N 个帖子、M 个文件、共 X GB」。
3. 分页列出 posts/ 下的 JSON，写入历史记录，文件状态标为「仅在云端」。卡片缩略图用 Drive 生成的缩略图，进入历史页即可浏览。
4. 用户选择：全部下载到本机（走传输服务，可续传），或保持仅在云端、打开时再下载。
5. 本机已有的同一文件（md5 相同）直接关联，不重复下载。

**删除与冲突**

- 文件内容不可变（以 md5 识别），只有帖子元数据可能冲突：按 updatedAt 后写者生效。
- 本地删除帖子时，云端怎么处理需要你决定（见「待决定问题」）。无论哪种，云端删除都先移到 Drive 回收站（Drive 保留 30 天），不直接永久删除。
- 两台手机同时开启备份时只保证不丢数据：同一文件靠 md5 去重，同一帖子的元数据后写者覆盖。不做实时合并，不读另一台的变化。

## 阶段 3–4：仅在云端与释放空间

只有「刚刚确认过云端副本完好」的文件才能从手机上删掉。删掉后历史记录、缩略图和 Live 配对信息都保留，卡片显示「仅在云端」。

**阶段 3：手动释放空间**

1. 历史页多选、或「云端备份」页的「释放空间」，列出可释放的帖子和可腾出的大小。
2. 删除前逐个向 Drive 确认文件存在且 md5Checksum 与本地记录一致；任何一个不一致或查不到，该帖子跳过并重新入上传队列。
3. Live 图的照片和视频只能一起释放，不拆开。
4. 删除复用 v1.12 的批量删除：一次 App 确认 + 一次系统确认，文案写明「云端仍保留」。

**查看与取回**

- 打开「仅在云端」的帖子：大图浏览先显示缩略图，同时把原文件下载到 App 缓存查看，缓存有上限，不入相册。
- 「保存回本机」：走传输服务下载到相册，校验 md5 后恢复为「已备份」。

**阶段 4：按规则自动释放**

- 默认关闭。可设置：只处理 N 天前下载的；只处理视频或大于 N MB 的文件；只在手机剩余空间低于 X GB 时运行。
- 首次启用时先展示会被释放的清单，用户确认后才生效。每天最多运行一次，结果以通知告知。
- 限制：Android 11 起，删除不是本应用创建的媒体文件必须弹系统确认；重装 App 或换机恢复后，文件就不再属于本应用。本应用创建的可以后台直接删；其余汇总成一条通知「有 N 个文件可释放」，用户点开时一次确认。若用户授予「媒体管理」特殊权限（MANAGE\_MEDIA，Android 12 起），可免去确认。是否引导申请该权限，见「待决定问题」。

## 数据模型变更与迁移

历史数据库只加字段、不改旧字段，升级后旧版本的备份仍能导入；传输任务单独放在 transfer.db，与历史记录分开。

| 位置 | 新增字段 | 阶段 | 说明 |
| --- | --- | --- | --- |
| 文件行 | md5 | 0 | 收尾复制时计算；旧记录在首次备份时补算 |
| 文件行 | cloudState | 1 | none / uploading / backed\_up / cloud\_only |
| 文件行 | driveFileId | 1 | Drive 文件编号，恢复和释放空间都依赖它 |
| 文件行 | cloudVerifiedAt | 3 | 最近一次向 Drive 确认 md5 的时间 |
| 帖子记录 | updatedAt | 2 | 元数据冲突时后写者生效 |
| transfer.db | 任务表 | 0 | jobId、方向（下载 / 上传）、状态、重试次数、所属批次、上传会话地址 |
| 备份导出 | schema 3 | 1 | 在 schema 2 基础上加以上文件字段；导入端兼容 2 和 3 |

- 每一步迁移都有单元测试：旧库升级、重复执行不出错、升级中途被杀后再次启动能完成。
- 旧记录补算 md5 要读整个文件，只在开启云端备份后、上传前逐个计算，不在启动时批量跑。

## 安全、隐私与日志

云端功能不引入任何服务器：数据只在用户手机和用户自己的 Drive 之间流动，开发者看不到任何内容。

- 权限只申请 drive.file，不申请读取整个 Drive 的权限。
- access token 只在内存中使用，不落盘。上传会话地址存 transfer.db，视为凭证：不进日志、不进备份导出、会话结束即删。
- 各平台的登录 cookie 仍然只用于下载：不上传、不进备份、不写入 transfer.db。
- Drive 上的帖子元数据只包含用户自己在 App 里本来就能看到的信息。
- 日志沿用现有规则：不记录 cookie、账号、token、完整网址、query、文件路径和 Drive 文件名；Drive 侧只记录状态码、字节数和耗时。新增日志前缀 \[XFER\]（传输服务）和 \[CLOUD\]（云端同步）。
- 登出或撤销授权时：停止所有上传任务，清除会话地址；本地文件和 Drive 上的文件都不动。
- 「仅在云端」的帖子在登出后仍显示记录和缩略图，打开时提示登录。

## 测试与验收

每个阶段都以真机验收为准，自动化测试必须覆盖「首轮任务」和「进程重启」，不能只测预先注入好状态的情况。这是 v1.12 的教训。

| 阶段 | 真机验收 |
| --- | --- |
| 0 | v1.12 回归清单全部通过；大视频新下载暂停 / 继续 3 次；断网、恢复；4G 与 Wi-Fi 切换；下载中划掉 App 后重开；悬浮球与 App 同时打开 |
| 1 | 登录、授权、取消授权；大视频上传中断网、划掉 App 后继续；Live 图成对上传；重复备份去重；Drive 空间不足 |
| 2 | 用第二台手机（或清数据后由你手动操作）恢复；记录数、文件数与云端一致；已有文件不重复下载 |
| 3 | 释放空间前后剩余空间变化；「仅在云端」帖子查看与保存回本机；云端文件被删后不允许释放 |
| 4 | 规则预览清单与实际释放一致；非本应用创建的文件只通过通知确认后删除 |

**故障注入（自动化）**

- 下载：服务器返回 200 代替 206；Content-Range 起点或总大小不符；传输中断开；写入时磁盘满；进程在收尾中途被杀。
- 上传：中途断开后查询进度；会话过期；token 失效；md5 不符；Drive 返回 403 配额不足。
- 释放空间：确认时云端文件已不存在或 md5 不符，必须拒绝删除本地文件。
- 测试中等待异步结果一律用 waitFor，涉及数据库的测试用独立数据库。

## 开源组件评估

每个阶段开工前先做一轮开源调研，只产出评估表，不写代码；确认没有合适的现成组件，再自己实现。

**规则**

- 可以直接依赖或复用代码：MIT、Apache-2.0、BSD。引入时在仓库记录名称、版本、许可证。
- GPL、AGPL、MPL 等 copyleft 项目：只看公开文档、设计说明和 issue 讨论，不读、不复制源代码（与 NEORUAA 的规则一致）。
- 评估维度：许可证、最近一次发布时间、是否满足本文档的规则（尤其是「一个文件一个写入者」「断点以磁盘为准」）、能否接入现有请求策略（请求头白名单、跳转白名单）、体积。
- 已知不用的：Android 系统 DownloadManager（无法控制跳转和请求头）。

**首轮候选（许可证与维护状态均需调研时核实）**

| 阶段 | 候选 | 用法 |
| --- | --- | --- |
| 0 传输 | OkHttp | 直接依赖，作为 HTTP 基础 |
| 0 传输 | Fetch、PRDownloader、Ketch 等 Android 下载库 | 评估能否直接用；不满足规则则只参考其续传与队列设计 |
| 1 上传 | Google API Client for Java（Drive v3） | 评估其可续传上传能否在进程重启后继续；不行则只用其模型类，上传协议自己实现 |
| 1 上传 | rclone 的 Drive 后端 | 参考可续传上传、md5 去重、错误重试的处理方式 |
| 1–3 备份 | Immich 移动端（Flutter 照片备份） | 功能与我们最接近（后台上传、释放空间）；若为 copyleft，只参考其文档与交互 |

## 风险与后续版本

最大的风险是阶段 0 重写了刚刚稳定下来的下载链路；应对办法是新旧并存、开发者选项切换、用 v1.12 回归清单验收。

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 阶段 0 引入新的下载问题 | 已稳定的 v1.12 体验退化 | 新旧并存一个验证周期；规则由结构保证，不堆补丁；故障注入测试先行 |
| 后台静默取 token 不可靠 | 自动备份时常停在「需要登录」 | 阶段 1 开工前做原型验证；不可靠则改为 App 前台时刷新 token、上传仍在后台 |
| 新系统对前台服务的限制 | 长时间上传被系统中断 | 上传本身可续传，被中断只是慢；必要时按系统版本改用 UIDT |
| 未经验证的 OAuth 应用 | 用户看到「未经验证」警告或授权有效期限制 | drive.file 等非敏感权限的发布要求在阶段 1 前核实；自用阶段可先用测试用户 |
| 免费 Drive 空间只有 15GB | 大视频很快占满 | 显示剩余空间；单文件上限设置；空间不足时暂停自动备份 |
| 释放空间误删 | 用户丢失文件 | 删除前实时校验云端 md5；云端删除先进回收站；单独的故障注入测试 |

**后续版本**

- v2.1：WebDAV / S3 等自建存储。传输服务和备份清单都按「存储后端」抽象设计，Drive 是第一个实现。
- v2.2：标签与分类目录，下载前后都可添加，历史页增加对应的展示模式和筛选条件；格式参照 OnlineAlbumPlugin。
- Live 图转 Motion Photo：本地显示 / 导出格式，云端始终保存原始成对文件。
- Pinterest 支持与浏览器扩展强化：阶段 1 之后，先评估官方 API（OAuth）与网页解析两条路线。
- 原生缩略图解码开关（从 v1.12 推迟）。
