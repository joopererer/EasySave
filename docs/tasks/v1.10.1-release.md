# v1.10.1 hotfix handover

Scope: **one** fix — a Xiaohongshu Live photo's motion part being saved as an
unplayable `.mp4` (HEIC in reality). No other change ships in this release (no
v1.11 work, no build 34–36 material).

- Branch: `hotfix/v1.10.1`, cut from `master` at `fd77107` (v1.10.0).
- Code commit: `a80b7ac` plus the documentation commit that adds this file.
- Parser release: `parser-v1.4.15` (tag on `a80b7ac`), channel manifest 11.

## 1. Root cause

Two defects line up.

**1.1 Parser: an image URL could fill the Live motion-clip slot.**
`extension/src/xhs.ts` builds a `type: "live"` item from the image entry:

```
own = entryKeyUrl ? {url: entryKeyUrl} : bestVideo([
  ...collectStreamCandidates(entry["stream"]),
  ...collectStreamCandidates(livePhoto["stream"]),
]);
item = { type: "live", url: <still>, videoUrl: own.url, fallbacks: <still fallbacks> }
```

`candidateFromEntry` accepted any stream entry that carried `masterUrl` /
`backupUrls` / `url`, and `rankVideoCandidates` ordered only by
watermark → audio → pixel area → bitrate. Nothing checked that the URL is a
video. A Live photo's still rendition can sit in the same stream map (or an
`originVideoKey` can name it); because the still is not watermarked and its
declared size (e.g. 3024×4032) dwarfs the clip's, `bestVideo()` picked the HEIC
original and wrote it into `item.videoUrl`. Reproduced with the shipped bundle
against a payload shaped like the real CDN data (stream carrying clip + still,
`url`-only stream entries, `originVideoKey` naming the still,
`livePhoto.stream`): in every one of those shapes `videoUrl` became the image
URL, while the plain fixture shape kept the clip.

**1.2 App: the plan trusted that URL and no byte was ever checked.**
`planFiles` (live branch) turned `videoUrl` into
`PlannedFile(isImage: false, filename …mp4)`. After the download,
`saveToGallery`/`exportNameFor` asked `provenance_dart.detectFormat`, whose
`isMp4Header` accepts any known top-level box — a HEIC file starts with `ftyp`,
so it was classified `MediaFormat.mp4`: saved as `<postId>_<seq>.mp4` with
`video/mp4`, and the MP4 XMP writer appended its `uuid` box at the end of a
still image. Result: a 0-second, unplayable `.mp4` with video provenance.

## 2. Fix

Parser (`extension/src/xhs.ts`, version 1.4.15):

- `xhsMediaKindOf(url)` — image / video / unknown from host, `/stream/` path,
  extension. Unknown stays acceptable, so an unseen CDN shape loses nothing.
- Video candidates skip image URLs: `candidateFromEntry`, absolute
  `originVideoKey` (note level and Live entry level).
- Still-image candidates skip video URLs: `imageUrlOf`,
  `xhsImageDownloadOrder`.

App:

- `app/lib/services/media_content_type.dart` (new): header-based identification
  of JPEG / PNG / WebP / GIF / HEIC / HEIF / AVIF (ftyp brands `heic`, `heix`,
  `hevc`, `hevx`, `heim`, `heis`, `hevm`, `hevs`, `mif1`, `msf1`, `avif`,
  `avis`) and MP4 / MOV (brand list **and** a `moov` box, found by walking the
  top-level box chain). Also `mediaKindOfUrl` / `filterMediaCandidates`, the
  Dart mirror of the parser classifier.
- `planFiles` / `planFilesForItem`: each file only carries candidates of its
  own kind; a list that would become empty is kept as-is (the header check
  then rejects it).
- `_finishFileOnce`: after the download, the file's own bytes are identified.
  A mismatch (image bytes for a video job, video bytes for an image job, or a
  movie without `moov`) deletes the temp file and moves to the next candidate;
  when no candidate is left the job fails (`下载到的文件不是视频/图片，已跳过`)
  and nothing is saved. Unreadable headers keep the previous behaviour.
- `export_names.dart` / `saver.dart`: album extension and MIME come from the
  detected container (`jpg/png/webp/gif/heic/avif/mp4/mov`).
- `download_provenance.dart`: a still container provenance_dart cannot embed
  into (HEIC / AVIF / GIF) is refused with the existing explicit message
  `该格式无法写入来源信息` before any writer runs, so no MP4 `uuid` box can land
  in an image. (That refusal is the v1.9 product rule for HEIC/AVIF.)

Version: `1.10.1` / versionCode `38`; parser `1.4.15`, channel manifest 11.
Existing wrong files are not touched; the CHANGELOG tells users to delete files
named `.mp4` that show 0 seconds and do not play.

## 10. Root cause

Three consumers computed "how many entries" and "what pairs with what"
independently, and the stored rows carried no explicit pair identity, so the
answer depended on mutable row bookkeeping:

1. **Post card count** — `record.savedFiles.length` (raw rows): a Live photo
   always counted 2. `history_cards.dart` (waterfall + list row).
2. **Home "最近保存"** — the subtitle also used the raw row count, and its
   viewer (`parse_page._openRecord`) built **one item per row**, with no
   grouping at all, so the motion clip became a second item. That item took its
   `type` from the post item, which is `live`, so the clip page was drawn as the
   still of the same Live photo: "两张相同的图，视频文件被当作普通图片显示".
   It could never pair, on any visit.
3. **History viewer** — `history_page._openRecord` grouped rows by `itemIndex`
   and paired a group only when it held exactly one image and one video (or the
   group had exactly two rows). Because the pairing input was the *current*
   `record.savedFiles` (rows the album scan has confirmed) grouped by a mutable
   index, the result followed whatever state the rows were in at that moment:
   with both rows at the same index it paired (one page); when the two rows were
   not in one group — an extra row from an earlier write of the same post, or a
   row whose index had not yet been reconciled by the album sync — it fell into
   the per-row branch and drew the clip as a second picture. The next visit
   re-read the rows after the scan had confirmed/repaired them, hence "第一次
  两张，第二次一张". Nothing about that was stable or intended.

The pairing data that *was* written at save time (`prov:pairId` inside the
file's XMP) was never stored in the history row, so the UI could not use it; the
v1.8.2-era rebuild scan (which reads it back from the album) is a separate code
path that only runs on demand.

## 11. Fix

- `app/lib/services/live_pairs.dart` (new): the one pairing function.
  `pairSavedMedia(files)` groups rows by the album name's sequence
  (`<sourceId>_<n>`, written by `cleanMediaFilename` at save time) and falls back
  to `itemIndex`; a group pairs into one Live entry only when it holds exactly
  one image and one video and, when both rows carry `prov:pairId`, the ids agree
  (the rebuild scan's rule). `savedMediaEntryCount(files)` is the count every
  consumer now uses. Pairing never looks at the extension or MIME type, so the
  v1.10.1 container detection cannot break it (a still named `.heic` pairs with
  its `.mp4` clip).
- `HistoryFile.pairId` stored in `files_json` (`pair_id`), written by
  `writeBatchHistory` for both rows of a Live photo (`<postId>#<itemIndex>`), so
  the rows carry the pairing identity from the moment the download finishes —
  no album scan or refresh required. Rows written earlier simply have no
  `pair_id` and pair by album name as before.
- `widgets/gallery_browser.dart`: `savedBrowserItems(...)`, one builder for both
  local viewers, built from `pairSavedMedia`. A Live pair becomes one
  `type: 'live'` page holding the still asset and the motion asset (LIVE badge,
  long-press playback); a clip that is *not* paired is typed `video`, never
  `live`, so it can never be shown as a duplicate still again.
- `history_page._openRecord` and `parse_page._openRecord` now both call
  `savedBrowserItems`; the two inline grouping/building loops are gone.
- Counts use `savedMediaEntryCount`: `WaterfallPostCard`, `ListPostRow`, the
  "最近保存" subtitle and the media view (`_groupMedia`, `_allKeys`).
- Version: `1.10.1` / versionCode `39` (build 38 stays the previous artifact).

Unchanged on purpose: physical rows per file, delete flows, `prov:pairId` inside
the files, the rebuild scan, sorting by file count, the library-wide "N 个文件"
totals.

# Round 3 — still saved from a preview instead of the original (build 41)

Real-device report on build 40 (log post `6a29621b000000003501e972`, Live items
2 and 9):

```
ci:jpg  result=transfer_failed reason=taskconnectionexception
img     result=transfer_failed            (or) sniff=heic result=retry:unsupported_provenance
ci      bytes=212806 sniff=heic result=retry:unsupported_provenance
webpic  bytes=76736  sniff=webp result=ok          <- this is what got saved
```

The saved still was the WebP **preview** and the history row was marked
"非原图". Provenance-writability had been ranked above image quality: a HEIC
original was set aside in the hope that a JPEG original would appear, and the
"all candidates are HEIC, keep it" fallback could never be reached because a
preview candidate was always left in the list.

## 16. Root cause (App side, two coupled defects)

1. **`rankStillCandidates` re-sorted previews ahead of originals.**
   `stillCandidateRank` ordered by container only (`jpg 0, png 1, webp 2,
   unknown 3, heic/avif/gif 4`). The parser's `downloadOrder` already ranks
   `jpeg → original → original_ci → default`, but the App's second sort moved a
   HEIC original (rank 4) behind a `sns-webpic-*` WebP (rank 2/3). Quality was
   therefore not the ordering key at all.
2. **`contentVerdictFor` deferred HEIC/AVIF whenever another candidate was
   untried** (`deferUnembeddable`), and each deferral re-enqueued a candidate
   while bypassing the transport attempt cap. So a HEIC original could never
   win while a preview was still in the list, and the "last candidate HEIC"
   accept branch was unreachable.

Both are App-side (`app/lib/services/*`); the parser never asked for a preview.

## 17. Fix — quality first, for Live stills and ordinary images alike

- `media_content_type.dart`: `isPreviewStillCandidate(url)` classifies
  preview-size derivatives (`sns-webpic-*`, `WB_PRV` / `H5_PRV`,
  `!nd_prv_*` / `!h5_prv_*`, down-sizing `imageView2` `/w/`, `/h/`,
  `thumbnail`). `stillCandidateRank` now ranks the quality class first
  (original `0`, preview `8`) and the container second, so an original HEIC
  beats a preview WebP and a jpeg original still beats a HEIC original —
  without ever issuing an extra request (it only reorders the stored list).
  `ContentVerdict.deferUnembeddable` is gone: an unembeddable still is
  `accept`.
- `download_manager.dart`:
  - the accept path logs `result=ok:provenance_skipped` and marks
    `notOriginal` only when the accepted candidate is a preview
    (`_markPreviewOnly` / `importsPreviewOnly`), keeping the existing "非原图"
    badge for previews;
  - `retryCapFor(batch, job)` gives a still one attempt per stored candidate
    (`min(urls.length, kMaxAttemptsHardCap)`), so every original candidate is
    tried and the preview is genuinely the last resort; videos keep the site
    rule. Used by `_failAttempt` and `_reconcileBatch`;
  - `_setAsideStill` / `DownloadJob.pendingStillPath` removed (nothing parks a
    still aside any more); old snapshots that carry the key simply ignore it;
  - no transcoding anywhere: HEIC / AVIF are saved in their own container, with
    extension and MIME taken from the bytes (`export_names.dart`, unchanged).
- Result for the reported post: candidate 2 (`img`, HEIC original) is now a
  success — saved as `<postId>_<n>.heic` with `image/heic`, provenance skipped,
  history row keeps `pair_id`, and the still + clip pair into **one** entry
  with no "非原图" mark.

## 18. `ci:jpg` always `TaskConnectionException`

Conclusion: **not an App-side candidate-construction defect**, so nothing in
the URL/authorization path changed in this hotfix and no parser version ships.

Evidence (code comparison, no device available here):

- `ci:jpg` is produced by the parser (`extension/src/xhs.ts`, `strip the
  !style suffix and serve through ci.xiaohongshu.com` +
  `?imageView2/format/jpg`). The App only forwards that string:
  `startBatch` → `planFiles` → `job.urls`, `MediaRequestPolicy.authorize`
  (`Uri.tryParse` + `toString()`, header/cookie rules), `DownloadTask.url`.
- `git diff fd77107 HEAD -- app/lib/services/download_manager.dart` shows the
  only change around candidate building is
  `imageUrls = rankStillCandidates(filterMediaCandidates(orderedMediaUrls(…)))`.
  `media_request_policy.dart`, `authorized_media_http.dart` and the vendored
  downloader are byte-identical to v1.10.0.
- The jpeg-first order itself came from `1ae7c32`, an ancestor of v1.10.0, and
  `downloadOrder` already put `jpeg` (the `ci:jpg` candidate) first there. So
  v1.10.0 requested exactly the same `ci:jpg` URL with the same headers, and a
  failure now is a request that failed there too — the origin, not the App.

Because the cause sits in the parser-emitted `ci.xiaohongshu.com` rendition (an
origin that does not answer from mobile networks) and this hotfix may not ship
a parser release, the candidate is kept (it can still succeed) and made cheap
to lose:

- each transport failure moves to the **next** candidate, and the same
  candidate is never re-requested (`service` rotates on `attempts`);
- the failure line now carries `host_class=site_media|cdn_media|other` and
  `cause=dns|tls|refused|timeout|unreachable|reset|other|http` — fixed tokens,
  never a URL, host name or query, so the next device log answers the question
  without leaking identifiers;
- build 40's `ci  sniff=heic` line already shows the `ci` original is
  reachable sometimes; under the new rule that HEIC is kept instead of being
  traded for the WebP preview.
