## 1. parser 选择规则（App 侧，进 v1.10.3）

### 1.1 真机日志说明了什么

```
[ParserUpdate] event=activated version=1.4.15 source=remote manifestVersion=11
[ParserUpdate] event=session … builtinVersion=1.4.16 builtinManifest=12 activeVersion=1.4.15 activeManifest=11
```

APK 里 12 号清单的 1.4.16 从未被启用。原因在 `ParserManager._selectVerified()`：它只调用
`store.load()`，只有「磁盘上没有任何可用 release」时才回落到内置 parser。也就是说，
**一旦设备下载过在线 parser，内置 parser 就再也不会被读到**（`recoverStateIfNeeded()`
在 state.json 存在时直接 return，连修复路径也不比较版本）。日志里没有 `[IgParse]` 行，
是因为运行的是 1.4.15 的 parser，它没有这条诊断。

### 1.2 现在的规则

`ParserReleaseStore.select()` 在**两侧都通过校验之后**比较 `manifestVersion`：

| 情形 | 结果 | `reason=` |
| --- | --- | --- |
| 内置更高 | 启用内置，水位线提到内置版本 | `builtin_higher` |
| 在线更高 | 启用在线（原行为不变） | `stored_higher` |
| 同号 + 同内容（payload 哈希相同） | 保持现状（当前是谁就用谁） | `same_sequence_same_content` |
| 同号 + 内容不同 | 保持现状，只记录 | `same_sequence_different_content` |
| 只有内置（没有 state.json） | 内置，且**不写** state.json | `builtin_only` |
| state 存在但 current 是 builtin | 内置 | `stored_none` |
| state 存在但 release 读不出来 | 内置 | `stored_unreadable` |
| 没有内置也没有在线 | 无 | `no_release` |

要点：

* **内置版本同样校验**：`SignedParserManifest.fromBuiltin()` 会做清单结构校验
  （APK 里的 schema）、语义校验（parserUrl / 域名 / 头），并核对 `assets/parser/parser.js`
  的 sha256；哈希不符直接抛 `builtin_parser_hash`，不会因为「是 APK 里的」就跳过。
  签名方面内置清单不经过网络信封（它由 APK 签名本身保护），在线清单仍走 Ed25519。
* **同号比较的是内容哈希，不是文件名**：内置清单的 payload 哈希是 `builtin-manifest.json`
  的字节 sha256，在线清单的 payload 哈希是签名信封里 `payload` 字符串的 sha256。两者
  由同一份 release payload 生成（`JSON.stringify(payload)`），实测 1.4.16/12 上二者
  完全相同（`6376813e…`），所以「同号同内容」的判定是可靠的。
* **水位线随选择更新**：`commitBuiltin()` 把 `state.json` 写成
  `current=builtin`、`highestAcceptedManifestVersion=内置版本`、`contentHash=内置 payload 哈希`。
  它**只升不降**：如果磁盘上已经接受过更高的序号（例如 release 目录还在但读不出来），
  水位线保持不变，让随后的在线检查仍能就地修复那一版。
* **启用内置之后不会「自打脸」**：在线通道如果发来同号同内容的版本，`checkForUpdates`
  以 `result=same reason=same_as_builtin` 结束，不下载、不激活、不报 equivocation；
  同号但内容不同的版本则被水位线判为 `parser_rollback`（`result=older`）——这正是
  「同号不同内容不得启用另一份」的另一半。
* 写 state 的仍然只有前台引擎（`_canUpdate`），后台引擎读取选择但从不写。

日志：

```
[ParserUpdate] event=select builtin=1.4.16/12 stored=1.4.15/11 chosen=builtin reason=builtin_higher
[ParserUpdate] event=activated version=1.4.16 source=builtin manifestVersion=12 configHash=…
[ParserUpdate] event=session stream=foreground app=1.10.3 builtinVersion=1.4.16 builtinManifest=12 activeVersion=1.4.16 activeManifest=12
```

`event=select` 每次进程只写一次（`getActiveScript()` 每次解析都会重跑选择，靠去重避免刷屏）。

### 1.3 测试覆盖（`app/test/v1103_parser_selection_test.dart`，7 项）

| 用例 | 断言 |
| --- | --- |
| 内置更高 | 内置生效、`state.json` 变为 builtin/12/内置哈希、日志 `reason=builtin_higher`、脚本是 APK 里的 |
| 在线更高 | 在线生效、`reason=stored_higher`、脚本是在线那份 |
| 同号同内容 | 仍用在线那份，`state.json` 一个字节都没改，`reason=same_sequence_same_content` |
| 同号不同内容 | 仍用当前那份（不启用另一份），`state.json` 不变，`reason=same_sequence_different_content` |
| 内置生效后的在线同号同内容 | `result=same reason=same_as_builtin`，只请求清单（`requests+1`），水位线仍是 12 |
| 内置也过哈希校验 | 错误 parser 字节 → `builtin_parser_hash`；正确字节的 payload 哈希与签名信封一致 |
| `select()` 直接调用 | 没有在线版本时 `chosen=builtin`，`stored=null` |

`app/test/parser_v2_update_test.dart` 原有 27 项全部保留，只把「安装一版低于 APK 序号的
release，然后期望它一直是活动版本」的用例改成高于内置序号（`above(n) = 内置序号 + n`）——
旧写法断言的正是本轮修掉的行为。

## 2. 解析缓存

### 2.1 真机现象

IG 登录后，App 内输入链接仍 `ParseCache event=hit` 命中登录前那次解析（登录墙上的封面），
悬浮球重新解析才正确。原因是 RAM 解析缓存（`ParsedHandoff` / `SharedParseCache`）只按
10 分钟 TTL 失效，与登录状态无关。

### 2.2 改动

* **登录状态变化即清空该站点**
  - 登录成功：`LoginExpiredBus.markLoggedIn()`（登录页轮询确认、`完成` 按钮、本地回调、
    「我的」登录返回）→ `clearParsedCacheForSite(platform, reason: 'login')`。
  - 退出：`auth.logout()` → `reason=logout`。
  - 检测到会话失效：`LoginExpiredBus.markExpired()`（解析返回 LOGIN_REQUIRED / 探针判失效）
    → `reason=session_invalid`。
  - 只是「再查一次已登录」的路径（「我的」页 `_refreshPlatform`）只 `clear()` 过期标记、
    不清缓存，否则每次进「我的」都会把缓存清空。
  - 清理范围：共享 RAM（原生 `clearParsed`，按条目里的 `site` 字段）+ 本引擎的
    `SharedParseCache` 兜底 + 该站点正在跑的 `_running` 任务登记。
  - 日志：`[ParseCache] event=cleared site=instagram reason=login`。
* **失败与降级结果不入缓存**
  - 失败本来就在写缓存之前抛出（测试固定住这条）。
  - 降级：新增 `ParseOutcome.degraded`；解析成功后如果结果只有 1 个图片项、没有尺寸/视频，
    且其 URL 恰好是页面 `meta[property="og:image"]`，就标为 degraded，照常返回给 UI 但
    **不写缓存**，日志 `[ParseCache] event=degraded site=instagram post=AbC123 reason=og_cover_only`。
    （这条是 App 侧兜底：装了 1.4.16 的 parser 之后 IG 这种页面会直接报
    `MEDIA_UNAVAILABLE`/`LOGIN_REQUIRED`，但旧 parser 或其它站点仍可能交出封面。）
* **解析中途登录状态变化**：按站点维护一个 generation 计数，解析结束时若代数变了，结果
  照常返回但不发布（`[ParseCache] event=dropped`），避免把旧会话的答案写进新会话的缓存。
* **历史页 / 首页「刷新」强制重新解析**：`forceRefresh` 不再并入正在进行的同一 key 的请求
  （那个请求可能正要返回缓存命中），并且跳过查询直接走网络。

## 5. 局限与未做的事

* **没有真机**：验证包的三条结论来自「APK 资源 + 真实选择代码」，见 3.3 的说明。
* **降级的判定是启发式**：只有「唯一图片项、无尺寸/无视频、且等于 `og:image`」才算降级。
  其它形态的降级（例如某站只给缩略图但尺寸齐全）仍会入缓存——parser 侧需要显式信号
  才能覆盖，这是下一轮（parser 1.4.17 提案里已有相关讨论）。
* **`stored_none` 时无法比较内容**：`state.json` 里 `current=builtin` 之后，磁盘上旧的
  release 不再被 `load()` 读取，所以同号不同内容只能在「当前是在线那一份」的方向上判定。
* **验证分支不推送**：`verify/ig-1.10.3-46` 只在本机，按要求不推送、不打 tag。

## 6. 真机验证步骤（用 `easysave-1.10.3-46-verify-ig.apk`）

准备：小米 M2002J9E（Android 12）。**不要卸载、不要清数据**（保留已有的 1.4.15/11 在线包
才验得到本轮的核心修复）。

1. **启动即生效**：覆盖安装后冷启动，`v16dl.log` 里应出现
   `event=select builtin=1.4.16/12 stored=1.4.15/11 chosen=builtin reason=builtin_higher`、
   `event=activated version=1.4.16 source=builtin manifestVersion=12`、
   `event=session … activeVersion=1.4.16 activeManifest=12`。
   再等一次启动检查，`event=check` 应为 `result=same reason=same_as_builtin`（或在线更新到
   更高序号时 `result=newer`），不应出现反复在 11/12 之间跳。
2. **IG 走修复后的 parser**：解析一条 IG reel，日志应出现
   `[IgParse] source=graphql|api|embedded_json mediaType=video …`；登录墙页面应直接报
   「未能获取该 Instagram 媒体，请检查 Instagram 登录后重试」而不是给出一张封面。
3. **登录后不再命中旧封面**：先不登录解析一条 IG 链接（失败或封面），然后在「我的」登录
   Instagram，回到首页输入同一条链接。期望日志先有
   `[ParseCache] event=cleared site=instagram reason=login`，随后是 `event=miss` + 真实解析，
   不再是 `event=hit`。
4. **刷新一定重解析**：历史页对已保存帖子点「刷新」，日志应是 `entry=history_refresh` +
   `event=miss`，不应出现 `event=hit`。
5. **退出登录**：退出 IG 后解析同一条链接，应有 `event=cleared … reason=logout`，随后重新
   解析（多半报需要登录），不会沿用登录时的结果。
