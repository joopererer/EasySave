# v1.12 tasks

## 后台引擎 `downloads-init` 4–8 秒的缩短（本轮只记录，不实现）

依据：[build57-download-start-evidence.md](build57-download-start-evidence.md) §6。
真机数值：`step=downloads-init` 4054 / 6648 / 6857 / 8305 ms（每次引擎重建后
第一次提交都要等这么久，用户在这一段时间里看不到任何进度）。

### 根因（证据文档 §6）

`DownloadManager.init()` 依次 await 四步，其中 `_loadAndReconcile()` 的耗时随
**索引里保留的终态批次数**增长，而不是随当前任务增长：每份终态快照都会再走一次
`_afterTerminal(recovered: true)`，其尾巴里最先被耗掉的是每个批次一次的原生
`notifications.cancel`（被 `historyStep('cancel-notification', timeout: 1s)` 限到
1 秒）。4 份历史批次 × 每次最多 1 秒 ≈ 4 秒，与 4054 ms 吻合；插件冷启动再叠加
就是 6–8 秒。

### 待办

- [ ] 已结算（`settledBy != null`）或 `historyWritten == true` 且通知已取消的
      终态批次直接跳过 `_afterTerminal`，只保留幂等的快照清理。
      —— 终态批次不该在每次引擎重建时重新结算一遍。
- [ ] `cancel-notification` 只在「本引擎本次会话显示过通知」时调用
      （`_lastShownPercent` 里有这个批次才有通知要取消），省掉全部历史批次的原生
      往返。注意：主引擎与后台引擎各自持有自己的 `_lastShownPercent`，跨引擎的
      通知要按「未显示过即无通知可取消」处理，不能把另一引擎的进度通知留下。
- [ ] `init()` 里的 `_loadAndReconcile()` 改为不阻塞入队：只在存在未终态批次时
      await，否则在后台跑完（`unawaited`），入队与首次进度不再等它。
      build 57 之后 `downloads-init` 超时已不影响任务，但缩短它仍能减少首次进度
      延迟。

### 约束

- 以上每一项都要单独做真机验证，并在证据文档里补 `downloads-init` 与
  `cancel-notification` 的前后数值；主机测试只能作为回归保护。
- 不得改变批次归属、结算语义（`settledBy` 只写一次）、历史写入的幂等性与
  失败快照的触发条件。
- 不得新增截止时间来「解决」耗时：本组问题的正确方向是减少不必要的工作。
