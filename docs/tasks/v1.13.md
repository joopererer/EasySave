# EasySave v1.13：统一后台传输服务（v2.0 阶段 0）

## 1. 基础信息

- **版本目标**：v2.0 阶段 0（统一后台传输服务）。
- **versionCode 规则**：正式 App 下一个 versionCode 必须 ≥ 82（v1.12.1 正式包使用 versionCode 81）。
- **设计依据**：[`v2.0-design.md`](v2.0-design.md)（阶段 0：统一后台传输服务）。

## 2. 目标与范围

### 目标
用自研的 Kotlin 前台传输服务（TransferService）替换现有的 `background_downloader` 插件及 App 层的断点续传/调度补丁代码：
- 下载只由传输服务驱动，App 主界面与悬浮球均作为客户端发送指令、监听状态流；
- 架构本身保证「七条规则」，根除 v1.12 中多层状态机冲突、竞态死锁与断点覆盖问题；
- 统一下载与后续 Google Drive 云端上传的底层传输抽象与调度器；
- 用户端功能与体验保持不变，以 v1.12 的全部回归清单为验收基准。

### 范围
- **包含**：
  * 基于 OkHttp 的自研统一后台传输服务（TransferService）；
  * 单一串行事件调度器（Scheduler）；
  * .part 物理临时文件与文件锁机制；
  * 基于 SQLite 的持久化任务存储（transfer.db）；
  * 逐跳拦截与清洗的媒体安全请求策略（复用现有规则）；
  * Flutter 通信桥接（MethodChannel + EventChannel）；
  * 新旧链路并存切换与平滑迁移机制。
- **不包含（排在后续阶段）**：
  * Google Drive 登录授权与云端备份队列（阶段 1）；
  * 换机恢复与备份同步（阶段 2）；
  * 仅在云端与空间释放（阶段 3–4）；
  * 实况照片合成为系统动态照片（Motion Photo，顺延至 v2.0 后续版本）。

## 3. 已知问题与设计约束

### 3.1 已知问题：阶段 0 新链路取代
- **现象描述**：在旧链路（`background_downloader`）中，当网络切换或异常断开时，存在「原生插件内部重连机制」与「Dart 侧 DownloadManager 自动重试机制」并存竞争的缺陷。在收到 `native_task_canceled` 后，底层 OkHttp 连接池/插件内部仍可能收到 206 Partial Content，随后触发 Dart 侧 `auto_resume 2/5`、`round_wait 15 秒` 与 `round_preempt` 冲突，导致任务状态震荡与非预期的抢占重试。
- **处置决定**：**不修**。该问题根源在于 `background_downloader` 插件自身具有黑盒内部状态机与重试逻辑，与业务层状态机产生多层重叠。此缺陷作为阶段 0（P0）通过自研 TransferService（单线程调度器 + 完全自主可控 OkHttp Worker）彻底取代旧链路的核心依据。

### 3.2 P0-3 性能与线程约束
- **严禁主线程 IO**：P0-3 的新 Finalizer 无论是来源信息嵌入、相册文件写入、还是数据库更新，**绝对不得在 Android 主线程做文件 IO 或繁重计算**，必须严格在后台 IO 线程或工作协程中执行，执行完毕后再通过主线程回调 Flutter。

## 4. P0-3 收尾方案调查

### 4.1 旧链路收尾的完整调用链
1. **来源信息写入（Embedding Provenance）**：
   - **调用起点**：`DownloadManager._embedProvenance`（位于 `app/lib/services/download_manager.dart`）。
   - **执行流与函数**：`prepareDownloadProvenance` -> `MetadataService.embedProvenance`（位于 `app/lib/metadata/metadata_service.dart`）-> 委托给外部包 `package:provenance_dart/provenance_dart.dart` 的 `pkg.MetadataService.embedProvenance`。
   - **线程与 Isolate**：**跑在根 Flutter UI Isolate（主 Dart 线程）中**。对于大视频（如 700MB+），使用 `Mp4WriteMode.rewrite` 在私有缓存中重写 MP4 容器（解析 box 树并流式写入新文件），由于未开启独立工作 Isolate（如 `Isolate.run`），其事件循环与异步流调度均在主 Isolate 上交错执行。
2. **复制进相册（Gallery Import）**：
   - **调用起点**：`DownloadManager` 调度 `saveWithConflictHandling`（`save_collision.dart`），传入 `saveToGallery`（`saver.dart`）或 `saveProvenancePair`（`provenance_pair.dart`）。
   - **通道调用**：通过 MethodChannel `easysave/provenance_pair` 发起 `saveMedia` 或 `savePair` 方法调用。
   - **原生端实现**：在 Android 原生侧由 `ProvenancePairWriter.kt` 接收，通过 `Thread { ... }.start()` 分发至后台线程执行 `PublicMediaWriter.save`（包含向 MediaStore `contentResolver.openOutputStream` 流式拷贝大文件、以及计算双重 SHA-256 校验和提取视频时长）。
   - **线程状态**：原生文件 IO 运行在后台 `Thread` 上；经过本次修复后，结果与异常通过 `mainHandler.post` 回调至 Android 主线程后再送入 Flutter，并在返回中附带 `thread="bg"`。
3. **写历史记录（History Db）**：
   - **调用函数**：`HistoryDb.instance().writeHistory(...)`。
   - **线程与数据库**：在 Flutter 侧通过 `sqflite` 执行，sqflite 插件内部维护有后台线程池写入 SQLite 数据库文件 `history.db`，写完后通过 Dart 流广播通知浏览列表与卡片更新。

### 4.2 HostService 后台 Flutter 引擎现状与复用分析
1. **HostService 引擎启动与生命周期**：
   - **启动方式**：通过 `FlutterInjector.instance().flutterLoader()` 完成初始化，构造 `val e = FlutterEngine(applicationContext, null, true)`，并在 `e.dartExecutor` 上执行 `executeDartEntrypoint(DartEntrypoint(loader.findAppBundlePath(), "backgroundMain"))`。
   - **生命周期**：由 `HostService` 单独持有，专为后台解析与分享弹窗服务。无操作 60 秒后触发 `releaseEngine()`，调用 `engine?.destroy()` 并 `stopSelf()`。
2. **能否被传输服务（TransferService）复用**：
   - **无法直接复用同一引擎**：
     * 前后台脱节：用户在前台主界面（`MainActivity`）触发下载时，`HostService` 通常并未运行，没有后台引擎可供复用；
     * 生命周期冲突：`HostService` 会在 60 秒空闲后随时销毁其引擎，若传输服务正在使用该引擎做收尾，会导致引擎被突发销毁从而中断收尾；
     * 引擎隔离：若由 TransferService 另起一个后台引擎，多引擎同时运行会消耗双倍内存（每个引擎底噪约 30MB-50MB）。
3. **启动引擎的实测耗时**：
   - 依据真机测试日志与历史设计记录（`docs/tasks/v1.6.md`, `v1.11.md`）：
     * 从调用 `FlutterEngine` 构造与 `executeDartEntrypoint` 到收到 Dart 侧 `ready` 回调，实测耗时在 **300ms ~ 800ms** 之间（低端机型冷启动可能超过 1200ms）。

### 4.3 三种收尾方案逐项评估

| 评估项 | 方案 1：交回 Flutter 主引擎 | 方案 2：服务启动后台 Flutter 引擎 | 方案 3：Kotlin 原生实现 Finalizer |
|---|---|---|---|
| **机制概述** | 任务完成时通过 EventChannel/MethodChannel 通知 Flutter 前台，由前台 Dart 代码完成来源信息写入、相册移入与历史记录 | 任务完成时若前台不可用，由 TransferService 启动类似 HostService 的轻量后台 Flutter 引擎，运行专用 Dart 入口做收尾 | 在 Android 原生层用 Kotlin 实现 Finalizer：解析/注入 XMP 来源信息、调用已有的 PublicMediaWriter 移入相册、操作 SQLite |
| **没有界面时能否完成** | ❌ **不能**。如果用户退出 App、切后台被系统杀死 Activity，前台引擎不存在，下载完成后无法收尾 | ✅ **能**。通过动态拉起后台引擎，即使无 Activity 也可完成收尾并自行销毁引擎 | ✅ **完全能**。纯原生前台服务独立完成，彻底解耦界面，系统杀掉 Flutter 进程不影响收尾 |
| **代码重复程度** | 🟢 **极低**。直接复用现有 Dart 侧全部成熟收尾代码（`MetadataService`, `saver.dart`, `HistoryDb`） | 🟢 **低**。复用现有 Dart 代码，仅需新增轻量 Dart 收尾入口和生命周期对接 | 🟡 **中等**。需用 Kotlin 原生重写 XMP box 注入逻辑（MP4/JPEG/PNG/WebP），移入相册逻辑则直接复用现成 `PublicMediaWriter.save` |
| **和 provenance-spec 对齐** | 🟢 **天然一致**。直接运行经过全套规范测试的 Dart 逻辑 | 🟢 **天然一致**。直接复用 Dart 逻辑 | 🟡 **需测试对齐**。需针对 Kotlin 实现编写单元测试，跑同样的 `provenance-spec` 测试向量以确保字节级/标签级严格一致 |
| **启动耗时与开销** | 0ms 额外开销，但依赖前台存在 | 每次启动耗时 300ms~800ms，额外占用 30MB~50MB 内存，存在多引擎 SQLite 锁竞争风险 | 🚀 **0ms 启动耗时**，零额外引擎内存占用，纯原生文件流与系统级 MediaStore 操作，性能最高 |
| **预计改动文件数** | ~3–5 个文件 | ~8–12 个文件 | ~10–15 个文件 |
| **综合风险** | 🔴 **高**。违背统一后台传输服务的核心诉求（无 UI / 锁屏 / 被杀时必须能独立稳定落盘） | 🟠 **中高**。多引擎生命周期脆弱，容易出现渠道丢失、冷启动耗时、内存激增等旧疾 | 🟢 **低**。逻辑纯粹清晰，无多引擎竞态，完全符合 Android 原生前台服务健壮性规范 |

### 4.4 推荐方案与理由
- **推荐方案**：**方案 3（Kotlin 原生 Finalizer）**。
- **推荐理由**：
  1. **彻底解耦界面与引擎**：统一前台传输服务（TransferService）的核心使命是实现「进程存活即可独立下载与收尾完成」。方案 1 在无界面时直接瘫痪；方案 2 引入多引擎会带来额外的内存消耗（30MB+）、冷启动延迟（300-800ms）及 SQLite 并发读写冲突风险。
  2. **相册导入原生基础完备**：当前向系统 MediaStore 移入文件的耗时 IO 逻辑（`PublicMediaWriter.save`）**本来就已经是 Kotlin 纯原生实现**，Dart 侧只是薄薄地调了一次 MethodChannel。
  3. **XMP 注入结构规范且单一**：EasySave 所支持的 MP4、JPEG、PNG、WebP 的 XMP/UUID 注入结构高度规范，Kotlin 端实现复杂度适中。配合共享的 `provenance-spec` 测试用例，可以在原生端实现 100% 字节兼容。
  4. **性能极致，杜绝主线程卡顿与 ANR**：原生 Finalizer 可直接在后台协程（`Dispatchers.IO`）上执行，大视频从 `.part` 嵌入来源信息后直接重命名/导入 MediaStore，避免跨 JNI 传递大数据，从根源上杜绝主线程阻塞与 ANR。

## 5. P0-3d 调查：旧链路 `ProvenancePairWriter.savePair` 与 Live 图配对机制

### 5.1 `ProvenancePairWriter.savePair`（媒体 + `.xmp` 边车成对原子写入）
- **代码位置**：
  - Kotlin 端：[ProvenancePairWriter.kt](file:///d:/workspace/IdeaProjects/EasySave/app/android/app/src/main/kotlin/com/james/easysave/ProvenancePairWriter.kt)（`register` L46–L104、`save` L137–L219、`saveLegacy` L222–L254、`deletePair` L106–L135）
  - Dart 端：[provenance_pair.dart](file:///d:/workspace/IdeaProjects/EasySave/app/lib/services/provenance_pair.dart)（`saveProvenancePair` L15–L72）
- **配对与命名规则**：
  - 用于携带 C2PA 内容凭证（不可直接篡改原文件嵌入 XMP）的媒体，将媒体文件与同目录 `.xmp` 边车成对保存至 `Download/EasySave/`。
  - 媒体文件名由 `ExportNames.cleanMediaFilename(postId, index, ext)`（`app/lib/services/export_names.dart:6-14`）生成 `<postId>_<index>.<ext>`；边车文件名由 `ProvenancePairWriter.sidecarName(mediaName)` 固定为 `<mediaName>.xmp`。
  - 写入前调用 `PublicMediaWriter.available` 校验目标目录无同名冲突，不静默覆盖旧文件。
- **写入顺序与失败回滚**：
  - **Android 10+（API 29+）**：使用 `MediaStore.Downloads.EXTERNAL_CONTENT_URI`（`RELATIVE_PATH = Download/EasySave/`）：
    1. 先以 `IS_PENDING = 1` 插入媒体行，拷贝字节后逐字节回读对比 SHA-256，并确认 `DISPLAY_NAME` 未被 Provider 改写；
    2. 再以 `IS_PENDING = 1` 插入边车 `.xmp` 行（MIME `PairSavePolicy.SIDECAR_MIME`），拷贝字节并回读对比 SHA-256 及 `DISPLAY_NAME`；
    3. 两者全部写入并校验通过后，遍历 `inserted` 列表将媒体与边车统一 `update(IS_PENDING = 0)` 发布。
  - **失败处理**：`try/catch` 捕获任意步骤异常后，遍历 `inserted` 列表执行 `resolver.delete` 并反查确认行数归零；若返回 Dart 侧后 `readProvenanceSidecar` 校验 `assetId` 不一致，调用 `deletePair` 成组清理媒体与边车。

### 5.2 旧链路 Live 图（实况照片 + 视频）配对与来源字段
- **代码位置**：
  - 任务规划与字段构造：[download_manager.dart](file:///d:/workspace/IdeaProjects/EasySave/app/lib/services/download_manager.dart)（`planFiles` L1086–L1110、`provenanceForBatchItem` L1157–L1180、`writeBatchHistory` L1241/L1270、`saveFinishedJob` L4789–L4801）
  - 文件命名规则：[export_names.dart](file:///d:/workspace/IdeaProjects/EasySave/app/lib/services/export_names.dart)（`cleanMediaFilename` L6–L14、`exportNameFor` L28–L33）
  - 历史与相册配对：[live_pairs.dart](file:///d:/workspace/IdeaProjects/EasySave/app/lib/services/live_pairs.dart)（L60–L165）
- **配对规则**：
  - **任务拆分**：`planFiles` 对 `item.type == 'live' && item.videoUrl != null` 规划出两个 `PlannedFile`（`isLivePhoto = true`，相同的 1-based `itemIndex`），分别下载静态图片和实况视频。
  - **关联字段（`pairId`）**：统一为 `${postId}#${itemIndex}`（即 `<sourceId>#<itemIndex>`）。写入 XMP 的 `ProvenanceRecord` 中通过 `prov:pairId` 字段记录该值，照片与视频具有相同的 `sourceId`、`itemIndex`、`itemCount` 与 `pairId`。
  - **文件命名**：两者在相册中均采用 `<sourceId>_<itemIndex>.<ext>`（例如 `<postId>_1.jpg` 与 `<postId>_1.mp4`），其中 `<ext>` 由各自文件头魔数嗅探结果决定；若遇同名冲突则追加 `-copyN`（如 `<postId>-copy2_1.jpg`）。
  - **新链路补齐目标（P0-3d）**：旧链路中 Live 的图片与视频各自独立进入 `saveToGallery`，缺乏跨任务的原子发布门控。新链路在 `TransferScheduler` 与 `TransferFinalizer` 中引入基于 `pairId` 的成对屏障与双 `IS_PENDING` 原子发布：任一任务失败/取消/暂停时另一方不单独进相册；全部下载完成后同时以 `IS_PENDING=1` 一遍写入再统一发布，被杀恢复时若未全部发布则删除未发布条目后成对重做，保证相册中「要么一对都在，要么一个都没有」。
