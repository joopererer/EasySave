# v1.10 数据驱动解析：已确认方案与执行记录

2026-10-28 用户确认。本文取代阶段一草稿中的冲突方案；只按本次指定阶段实施。

## 用户决定与协议

1. 外层为 {"schemaVersion":2,"payload":"<清单 JSON 原文字符串>","signature":"<hex>"}。Ed25519 仅签 payload 的 UTF-8 字节，不做 JSON 规范化。沿用 App 现有公钥。App 缓存收到的原始文件字节，每次使用前验签与校验 parser 哈希。
2. 仅前台 Flutter 引擎检查、下载、验证和激活；后台引擎只读已激活版本。激活生成只含站点 id、域名及路径规则的链接识别视图，原子写 App 私有目录。Kotlin 不验签、不承担安全判断；所有真正解析与网络授权在 Flutter 中复核。
3. parserUrl 固定为对应 parser-v 标签的 GitHub Release 附件。CI 顺序：测试→构建→签名→上传附件→读回校验→最后提交 master 的 spec/v2/manifest.json。加 concurrency，cancel-in-progress=false。不做草稿 Release、内容寻址名或 CAS。
4. spec/manifest.json 与 spec/parser.js 冻结在 1.2.4，供 ≤1.9.x App/旧扩展使用，以后不再更新。v2 使用独立 URL；内置 parser 可通过正常 App 构建更新。
5. 暂不做 DNS 重绑定、内网 IP 检查、公共后缀表、远程图标或签名过期时间。Cookie 域必须在本站清单授权，匹配仅 H==D 或 H 以 "."+D 结尾；URL 必须使用 HTTPS，禁止伪装 host 与 userinfo。请求头白名单为 Referer/Origin/User-Agent/Range，Cookie 值只在内存。
6. TikTok 按实际媒体 URL 向系统 CookieManager 查询，媒体主机预期为 *.tiktok.com；列为 2b 真机第一项验证，不提前判为高风险。
7. 备份 v2 originalUrl 原样保留（含 xsec_token）；mediaId 继续导出，恢复只当待核实线索。其余按备份分析执行。
8. 阶段：2a 可信更新→2b 四站迁移/请求策略/识别视图接入→真机→2c 备份 v2→2d 抖音（用户链接与匿名实测前置）→真机。

## 清单与应用方案

Schema：spec/sites-manifest.schema.json。外层 payload 是字符串，contentSchema 仅为格式注解；构建与 App 必须显式 JSON 解码后验证 $defs/payload，不能只验证外层。
spec/sites-manifest.example.json 覆盖小红书、IG、X、TikTok、抖音，签名与哈希为占位，不能发布。抖音默认关闭，CDN 未实测不擅自授权。parserAbi=1 表示当前 EasySaveParser 调用协议，2a 不引入新模块 ABI。
源配置：config/sites.json 定义站点字段，config/parser-release.json 定义发布序号/minAppVersion/Release URL 模板与兼容平台配置；parserVersion 从 spec/PARSER_VERSION 读取。脚本不写死站点或版本。
下载要求按每个 image/video/motion/poster/fallback 资源声明 headers、cookieDomains、expiresAt、transport/resumable；App 对每个请求与重定向重新校验，不从站点主页取 Cookie 转发给媒体域。2b 才迁移现有下载路径。
站点 id、platform、displayName、creditName、域/路径、短链、规范化、加载方式、登录提示、parserModule、元数据 authorIdRule/minAppVersion 读取清单；未知站点显示通用本地图标，平台名开放为小写标识。
站点算法与页面结构可放签名 TS 模块；OS 权限、CookieManager、MediaStore/SAF、元数据写入、文件配对、生命周期、更新验证器保留原生/可信 App 实现。Kotlin 识别视图只作入口提示，不授权请求。
前台激活：候选完整验签/哈希/兼容性/站点语义→独立版本目录写入并 flush→单一状态文件原子替换（当前、上一个可用版本、水位、payload 内容哈希）→更新识别视图。后台不写缓存或视图。启动损坏时验证上一个版本或内置；不会降低水位。
防回滚：新序号低于最高已接受序号拒绝；同序号仅相同 payload 内容哈希可复用。整包 minAppVersion 不满足则不激活，单站不满足则过滤该站。失败保留当前版本；本地已验证旧版本应急回退不等于接受远程降级。
读取清单和 parser 时每次从原始字节重验，不靠内存已验标记。启动可回退不删除坏文件以外的可用版本。24h + ETag 节流，只有前台更新。
Release 和 master 不具跨系统事务：上传/读回失败不改通道，最后 push 失败时客户端仍用旧包；可重跑恢复。不可变标签附件避免 manifest/parser 的可变路径双读问题；并发串行并检查序号防乱序。实际发布由用户决定。

## 6. 备份整理：保留结构和本地身份，删除媒体 URL

代码证据：backup_service.dart:57–68 原样导出 itemsJson 对象，:86 写 provenance.source.url，:118 写 originalUrl，:125 写 items；backup_model.dart:64,71,91 等序列化；core/models.dart:81–94 可写出所有媒体地址。

### 第 1 项 历史记录首项重复（回归）

### 第 2 项 TikTok 解析失败（FormatException / INVALID_PAGE）

根因：
- `ParserHooks.call` 只接受 `{value: …}`，`evaluateJavascript` 返回 `null`/空串或非 JSON 时直接 `FormatException('Invalid parser hook result')`，**不写任何日志**；而页面层 `catch (_)` 把它统一盖成 `INVALID_PAGE`，于是第一次报原始异常文案、之后每次重试都只剩「页面内容无法识别，可能已改版」，且全程没有 `[ParseMismatch]`。重试本身没有缓存失败状态（每次新建 Headless WebView，`getActiveScript` 每次重新验签），无法恢复是因为失败是确定性的、且被掩盖。
- 与 v1.9.0 对照：v1.9.0 `onLoadStop` 里 `canonicalTiktokUrl(uri)` 为 `null` 时**直接 return 继续等待**，只有拿到 canonical 才跳转/解析。v1.10 的 `navigate` hook 在「已在规范页」时返回空值（null/undefined/空串），旧校验把它当格式错误——这正是第二次加载必然失败的原因。

修复：
- `navigateStep`（`parse_service.dart`）复刻 v1.9.0 语义：`{wait:true}` 等待；`{url}` 且未跳转过才跳转一次；**空答案**在「当前地址已是本站作品页」时直接解析、否则继续等待；站点外目标返回 `invalid` 并记 `check=NAVIGATE`。
- `ParserHooks.call` 拆出纯函数 `unwrapHookResult`：空答案在 `install/navigate/account` 视为 `null`、`ready/prepare` 视为 `false`；其余不合格结果先写 `[ParseMismatch] check=HOOK_RESULT site=… post=- hook=… expected={value:<json>} actual=type=… fields=…` 再抛 `FormatException`（只记 hook 名、类型、字段名，不含地址与查询参数）。
- 页面层兜底 `catch` 记 `check=UNCAUGHT actual=type=<异常类型>`，不再无声吞掉。
- 测试：`app/test/tiktok_retry_recovery_test.dart`（短链落地页等待 → 规范页跳转一次 → 已在规范页且 hook 返回空值仍解析；HOOK_RESULT 日志字段与脱敏）。

| `formatVersion` | 与 `schemaVersion` 相同（`2`）。只认识 v1 的旧 App 读到 `2` 会按既有规则拒绝并提示升级，而不是错读 |
| `exportedAt` / `appVersion` / `provenanceSpecVersion` | 导出时间（带时区）、写入的 App 版本、规范版本（`0.1.8`） |
| `settings` | 与 v1 相同的非敏感设置 |

### 帖子 `posts[]`

| 字段 | 说明 |
|---|---|
| `platform` | 统一站点身份（规范平台名，如 `xiaohongshu`、`instagram`、`x`、`tiktok`） |
| `sourceId` | 帖子 ID |
| `canonicalUrl` | 按规范 0.1.8 规范化的原帖地址（provenance_dart `normalizeUrl`）；带 query 时省略此字段 |
| `originalUrl` | 用户保存时的链接原样，包括 `xsec_token`；全文件中唯一允许带 query 的 URL |
| `title` / `author.name` / `caption` | 标题、作者名、正文 |
| `aiLabel` / `aiLabelSource` | AI 标签原文与来源 |
| `savedAt` | 保存时间 |
| `status` | `success` / `partial` / `failed`：没有已保存文件为 failed；有文件且记录了下载失败原因为 partial；否则 success |
| `failureReason` | failed / partial 的简短原因（如 `HTTP 403`、`存储空间不足`），可省略 |
| `files[]` | 见下表；下载失败的帖子为空数组，同样写入 |

### 文件 `posts[].files[]`

| 字段 | 说明 |
|---|---|
| `itemIndex` | 原帖中的 1 起始位置，不重编号 |
| `mediaType` | `image` / `video` |
| `filename` / `relativePath` | 相册显示文件名与相对路径 |
| `size` | 文件字节数（下载时记录；旧记录导出时从 MediaStore 读取，读不到则省略） |
| `assetId` | 来源信息中的 `prov:assetId` |
| `mediaIdHint` | 写备份那台设备的 MediaStore id，仅作提示 |
| `savedAt` | 保存时间 |
| `itemCount` / `capturedBy` | 写入文件时的来源信息原值，没有则省略 |

只导出已定位或带物理身份（mediaId / assetId）的文件，包括本机已找不到的文件；仅凭文件名推断、没有身份的旧行不导出。

### v1 → v2 差异

| v1 | v2 |
|---|---|
| `formatVersion: 1` | `schemaVersion: 2`，`formatVersion: 2` |
| `posts[].items[]`：媒体、视频、封面、缩略图、备用 CDN 地址（带签名和过期参数） | 删除 |
| `files[].provenance`（含 `source.url` 等，重复原帖地址） | 删除；`itemCount`、`capturedBy` 直接放在文件上 |
| `files[].mediaId`（恢复时直接信任） | `mediaIdHint`，恢复时必须核对文件名和大小 |
| `createdAt` / `authorName` | `savedAt` / `author.name` |
| 无帖子状态；失败帖子恢复后与成功帖子无法区分 | `status` + `failureReason`；失败帖子恢复后显示“下载失败，点击重试” |
| 无规范地址、无文件大小 | `canonicalUrl`、`size` |

读取 v1 时：丢弃 `items` 和 `provenance` 中的地址，只保留 `itemCount`、`capturedBy`；`mediaId` 作为提示；没有文件的帖子按失败处理；其余按 v2 规则恢复。备份中不得出现 cookie、账号凭据或登录信息（`validateNoSensitiveKeys` 键名审计 + 测试中的 URL 扫描）。

### 恢复时的文件匹配

1. 相册文件的来源信息：XMP 中的 `sourceId` + `itemIndex`（同一平台），或 `assetId`。
2. 文件名约定：`<sourceId>_<itemIndex>` 或备份中的文件名（文件名必须包含该帖子的 sourceId，`IMG_0001.jpg` 这类通用名不算）。
3. `mediaIdHint`：该 id 的文件名与备份一致、大小与 `size` 一致才采用；备份没有 `size`（v1）时不采用。

任何一步的候选，只要其来源信息指向其他帖子或其他 itemIndex 就被排除；同一次恢复中一个相册文件只关联一次；本机已定位的文件保持不变。匹配不到的文件记为“不在本机”（`notFound`）；无法建立相册索引（无权限且无原生桥）时记为 `unknown`，同样不使用提示。失败与部分成功的帖子保存其状态，历史页显示“下载失败（原因），点击重试”，重试从 originalUrl 重新解析。同一份备份恢复两次结果相同。日志：`[BackupRestore] event=done schema= posts= files= viaProvenance= viaFilename= viaMediaIdHint= notOnDevice=`，`[Backup] event=export schema=2 posts= files= bytes=`（无 URL）。

### 未纳入 v2 的调研建议

第 6 节建议的媒体结构摘要（type / isGif / width / height / duration）不在本轮需求的字段清单中，v2 未包含：恢复后的帖子不再带 `items_json`（本机已有记录时保留本机的），Live 配对按文件行 `(itemIndex, isImage)` 重建，GIF 标记与封面比例不随备份恢复。

### 体积

同一份历史（40 个帖子、160 个文件，带签名 CDN 地址）：v1 布局 227,985 字节，v2 89,447 字节（约 0.39 倍），见 `build31_backup_v2_test.dart`。

三层备份机制不变：App 私有 JSON、Android 自动备份、SAF 文件夹轮换 7 份、内容去重、秒级文件名；轮换规则仍只在 Dart 中实现。SAF 写后回读校验改为要求 `schemaVersion == 2`。
