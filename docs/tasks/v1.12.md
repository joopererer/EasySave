### 大文件收尾优化技术评估（Backlog Evaluation）
**背景与痛点**：
真机日志显示，732MB 视频在下载完成后，收尾阶段实测耗时（`finish_timing` 打点数据）：
1. 样本 1（日志第 172 行）：`provenance_ms=30902`（约 30.9 秒，`_embedProvenance` 写入来源信息），`import_copy_ms=10309`（约 10.3 秒，`saveWithConflictHandling` 复制到相册），总计约 41.2 秒；
2. 样本 2（日志第 913 行）：`provenance_ms=19339`（约 19.3 秒，写入来源信息），`import_copy_ms=7416`（约 7.4 秒，复制到相册），总计约 26.8 秒；
3. 两次完整落盘与磁盘 I/O 导致存储占用峰值达原文件的 2 倍（约 1.5GB），且在闪存较慢的设备上收尾耗时进一步拉长。所有数据均来自真机日志实测打点。

**演进方向评估**：
- **方案 A：单遍流式复制 + 边写入来源信息（One-pass Streaming）**：
  在将私有目录文件复制到 MediaStore 的 `OutputStream` 过程中，通过流式解析 MP4 容器结构，在流动写入相册的同时完成 `moov` 盒定位与元数据注入，仅需一次 I/O 遍历，节省来源信息单独写入耗时与中间临时存储。
- **方案 B：SAF / MediaStore 直接落地下载（Direct Download to MediaStore）**：
  在下载发起时即通过 `MediaStore.createInsertRequest` 创建 `IS_PENDING = 1` 的相册 URI，下载器直接以 Range 写入目标流，下载完毕后关闭流并更新 `IS_PENDING = 0`。
- **结论与排期**：
  由于 Android 10+ 分区存储与 SAF 流式随机写（断点续传 seek）对 ContentProvider URI 的支持存在机型碎片化差异，且可能影响断网恢复时临时文件的保护，当前 build 69 先行落地细分进度阶段文案（`写入来源信息` / `复制到相册`）保障良好用户感知；流式单遍写入架构列入 v1.13 技术重构 Backlog 深入预研。

### build 70：大文件断点续传收敛终版与跨引擎进度同步
本版为断点续传收尾版，采用严格的兜底规则彻底闭环续传自愈链路，不再追加其他续传改动（待真机验证）：
1. **活跃任务数超时保护（Item 0d）**：

2. **悬浮球跨引擎实时进度呈现（Item 1）**：
   - 根因：`DownloadJob.toJson()` 与 `fromJson()` 未包含 `progress` 字段，跨引擎通过 SharedPreferences 同步时进度丢失归零。
   - 序列化补全：`DownloadJob.toJson()` 添加 `'progress': progress`，`fromJson()` 正确解析 `progress`。
   - 节流落盘：拥有批次的引擎在 `_onUpdate`（TaskProgressUpdate）与会话下载 `onProgress` 中按 1s 或 1%（0.01）增量节流写入 `SharedPreferences`。
   - 只读呈现：主程序作为外部观察者读取快照并更新内存视图，直接展示实时进度与「正在下载 (悬浮球)」，不触发越权接管。
3. **断点续传兜底规则（Item 2，收尾终版）**：
   - **Rule 2a（部分字节绝对保护）**：凡临时文件存在且字节数 $> 0$ 的任务，任何连接中断、握手超时或续传异常绝不判定终态失败，绝不删除临时文件，统一进入「下载中断」（`JobState.paused`）。
   - **Rule 2b（断点自愈与指数退避）**：进入中断后，网络恢复时自动以实际磁盘文件大小为起点发起续传重试，最多重试 5 次，退避间隔分别为 5s、15s、30s、60s、120s。日志输出 `auto_resume n=<次数>/5 from_bytes=<已下载字节> reason=<上次失败原因>`。
   - **Rule 2c（重试耗尽安全挂起）**：5 次重试均失败后，任务安全停留在「已中断，点继续」（`JobState.paused`，`error = '已中断，点继续'`），保留断点与临时文件，用户手动点击即可通过已验证的暂停/继续链路恢复下载。
   - **Rule 2d（临时文件清理严格收敛）**：部分临时文件的清理严格限制在四种明确场景：① 服务端返回 200 不支持 Range；② Content-Range 总大小不一致；③ 用户主动取消任务；④ 用户主动删除任务。清理时统一记录日志 `temp_discard reason=...`。
   - **Rule 2e（原生插件 resume_failed 语义收敛）**：在 `DownloadTaskRunner.kt` 中，`resume_failed` 严禁截断或删除临时文件，必须完整保留临时文件并向 Dart 返回失败，交由 Dart 兜底保护。
   - **Rule 2h（网络切换与 3s 稳定性窗口）**：
     * 网络连接恢复（`NET_CAPABILITY_VALIDATED`）后，启动 3 秒稳定性窗口，无跳变后才触发 auto-resume；
     * 下载中网络类型切换（Wi-Fi <-> 蜂窝）：任务置为中断，立即以当前断点自愈续传（不计入 5 次重试上限）；
     * 状态流转记录日志：`network_change from=wifi|cellular|none to=... action=wait_stable|resume`。

### build 71：悬浮球轮次判定修复与已入库状态防二次处理
1. **轮次判定与防内存快照冲刷（Item A1）**：
   - 根因分析：
     * 现象：build 69 悬浮球「全部下载」或「选择下载」时，第一张图起卡在「正在保存到相册」，90-180 秒后才由 watchdog 触发完成，日志出现 46 条 `stale_update taskId=…-0-1-r1-try1` 全部来自 `[background]`，`[main]` 无一条。
     * 原因一（快照冲刷）：build 69 在 `background_entry.dart` 循环中引入了 `reloadBatchSnapshot`，每 500ms 重载快照并执行 `_batches[batchId] = updated`，将后台引擎内存中的活跃批次对象覆盖为磁盘中持久化的旧快照（其中 `currentTaskId` 为 null 或旧值）。
     * 原因二（后缀比较）：非断点续传图片任务使用 `-tryN` 后缀，重试或字符串全等比较导致当前轮次更新被误判为过期。
   - 修复措施：
     * `reloadBatchSnapshot` 中加入属主保护：当批次属于当前引擎且非终态时，不将磁盘快照覆盖内存中的活跃实例。
     * 轮次匹配规则：仅提取与比较轮次编号（`-rN` 中的数字 $N$）。当 $N < \text{job.round}$ 时判定为 stale；当 $N \ge \text{job.round}$ 时视为当前或更新轮次，更新 `currentTaskId` 并推进 `job.round`，`-tryN` 不参与过期判定。
2. **已入库/已完成防二次处理（Item A2 & A3）**：
   - 统一校验（`_isAlreadySaved`）：检查 `job.saved`、`job.state == JobState.done`、`job.mediaId != null`、`job.assetId != null` 或 HistoryDb 中是否存在该 post 对应文件。
   - 全链路跳过：无论 watchdog、reconcile、retry 还是任务完成，发现已入库/已完成一律记录 `[V16DL] finish_skipped taskId=… index=… reason=already_saved` 并安全跳过，绝不再调用 `finishFile`。
   - 临时文件丢失兜底：收尾阶段（`_finishFileOnce`）若临时文件不存在，先检查 `_isAlreadySaved`；已入库的按成功处理（`job.saved=true`, `job.state=done`），不得标记为失败或提示「文件丢失，请重试」。
3. **精准 Watchdog 延迟计算（Item A4）**：
   - 修正延迟计算时序：在更新 `job.lastProgressAt = now` 之前计算延迟。
   - 优先以 `job.downloadCompleteAt`、临时文件修改时间 `lastModifiedSync()` 或前次进度时间计算真实时差，确保 `watchdog_delay_ms` 反映真实等待耗时且绝不为 0ms。
4. **测试缝隙与生产代码清理（Item B1）**：
   - 彻底删除 `_countActiveNativeTasks` 中所有面向测试环境的分支逻辑（`Platform.environment.containsKey('FLUTTER_TEST')` 等）。
   - 生产代码发生超时或异常时一律稳妥返回 1。
   - 单测通过注入测试缝隙（`allRecordsForTesting`）在 `setUp` / `tearDown` 中成对维护。
