### 大文件收尾优化技术评估（Backlog Evaluation）
**背景与痛点**：
真机日志显示，732MB 视频在下载完成后，收尾阶段实测耗时（`finish_timing` 打点数据）：
1. 样本 1（日志第 172 行）：`provenance_ms=30902`（约 30.9 秒，`_embedProvenance` 写入来源信息），`import_copy_ms=10309`（约 10.3 秒，`saveWithConflictHandling` 复制到相册），总计约 41.2 秒；
2. 样本 2（日志第 913 行）：`provenance_ms=19339`（约 19.3 秒，写入来源信息），`import_copy_ms=7416`（约 7.4 秒，复制到相册），总计约 26.8 秒；
3. 两次完整落盘与磁盘 I/O 导致存储占用峰值达原文件的 2 倍（约 1.5GB），且在闪存较慢的设备上收尾耗时进一步拉长。所有数据均来自真机日志实测打点。

**演进方向评估**：
- **方案 A：单遍流式复制 + 边写入来源信息（One-pass Streaming）**：
  在将私有目录文件复制到 MediaStore 的 `OutputStream` 过程中，通过流式解析 MP4 容器结构，在流动写入相册的同时完成 `moov` 盒定位与元数据注入，仅需一次 I/O 遍历，节省来源信息单独写入耗时与中间临时存储。
- **方案 B：SAF / MediaStore 直接落地下载（Direct Download to MediaStore）**：
  在下载发起时即通过 `MediaStore.createInsertRequest` 创建 `IS_PENDING = 1` 的相册 URI，下载器直接以 Range 写入目标流，下载完毕后关闭流并更新 `IS_PENDING = 0`。
- **结论与排期**：
  由于 Android 10+ 分区存储与 SAF 流式随机写（断点续传 seek）对 ContentProvider URI 的支持存在机型碎片化差异，且可能影响断网恢复时临时文件的保护，当前 build 69 先行落地细分进度阶段文案（`写入来源信息` / `复制到相册`）保障良好用户感知；流式单遍写入架构列入 v1.13 技术重构 Backlog 深入预研。

3. **断点续传兜底规则（Item 2，收尾终版）**：
   - **Rule 2a（部分字节绝对保护）**：凡临时文件存在且字节数 $> 0$ 的任务，任何连接中断、握手超时或续传异常绝不判定终态失败，绝不删除临时文件，统一进入「下载中断」（`JobState.paused`）。
   - **Rule 2b（断点自愈与指数退避）**：进入中断后，网络恢复时自动以实际磁盘文件大小为起点发起续传重试，最多重试 5 次，退避间隔分别为 5s、15s、30s、60s、120s。日志输出 `auto_resume n=<次数>/5 from_bytes=<已下载字节> reason=<上次失败原因>`。
   - **Rule 2c（重试耗尽安全挂起）**：5 次重试均失败后，任务安全停留在「已中断，点继续」（`JobState.paused`，`error = '已中断，点继续'`），保留断点与临时文件，用户手动点击即可通过已验证的暂停/继续链路恢复下载。
   - **Rule 2d（临时文件清理严格收敛）**：部分临时文件的清理严格限制在四种明确场景：① 服务端返回 200 不支持 Range；② Content-Range 总大小不一致；③ 用户主动取消任务；④ 用户主动删除任务。清理时统一记录日志 `temp_discard reason=...`。
   - **Rule 2e（原生插件 resume_failed 语义收敛）**：在 `DownloadTaskRunner.kt` 中，`resume_failed` 严禁截断或删除临时文件，必须完整保留临时文件并向 Dart 返回失败，交由 Dart 兜底保护。
   - **Rule 2h（网络切换与 3s 稳定性窗口）**：
     * 网络连接恢复（`NET_CAPABILITY_VALIDATED`）后，启动 3 秒稳定性窗口，无跳变后才触发 auto-resume；
     * 下载中网络类型切换（Wi-Fi <-> 蜂窝）：任务置为中断，立即以当前断点自愈续传（不计入 5 次重试上限）；
     * 状态流转记录日志：`network_change from=wifi|cellular|none to=... action=wait_stable|resume`。

### 已知限制
- **网络极不稳定时可能需要手动点继续**：大文件在连续 5 次断点续传重试均遇网络异常失败后，系统将停止自动重试并将任务置为「已中断，点继续」，完整保留已有进度与临时文件；待网络环境稳定后，用户在卡片或队列中点击「继续」即可从断点恢复下载。

### build 72：批次活跃任务查询与结算解耦及自愈修复

#### 架构复盘与经验教训（Item B2）
- **死锁根因**：在 build 70 中引入了「原生活跃任务数超时保护」（`_countActiveNativeTasks` 500ms 超时），并规定「超时一律视为仍有任务在运行（返回 1）以防止提前结算」；然而该方法通过 `FileDownloader().database.allRecords()` 扫描插件整个 SQLite 数据库表，在真机上记录较多时每次查询耗时均超过 500ms（产生 `active_count_timeout`），超时返回 1 又导致 `_afterTerminal` 认为 `active_native=1` 并永久阻塞结算（`batch_settle_blocked`），即使所有图片/视频已入相册（`gallery import done`），批次也永远无法进入结算，历史记录永久停留在 `download-placeholder files=0`。
- **保护设计准则**：今后此类防早结保护在真机上必须有明确的耗时基准与统计数据支持，绝不可将插件全量扫描作为阻塞条件，且超时不得做永久悲观阻塞。

#### 核心修改
1. **以 App 自身任务状态为首要准则结算（Item A1）**：
   - 当批次内每一项都已保存（`job.saved` 或 `job.state == JobState.done`）、已取消（`job.state == JobState.canceled`）或已确认失败时，直接完成结算，绕过原生插件活跃任务查询，日志记录 `batch_settle reason=all_completed files=<n>`。
2. **定向任务查询与耗时打点（Item A2 & A4）**：
   - 仅在 App 认为存在未完成或未确认失败的项时，才针对这些项当前轮次的 `taskId` 执行定向单任务查询（`FileDownloader().database.recordForId(taskId)`），单次查询超时设为 3 秒，严禁调用 `allRecords` 扫描全表。
   - 记录耗时日志：`active_query taskIds=<数量> ms=<耗时> result=active|idle`。
3. **超时防死锁退避降级（Item A3）**：
   - 定向查询若发生超时或异常，记录日志 `active_count_timeout id=<batchId> error=...`，延迟 30 秒后重试。
   - 连续 3 次超时后，彻底打破死锁，以 App 自身记录的状态为准完成结算，并记录日志 `batch_settle reason=native_query_unavailable`，确保历史记录正确写入文件行。
4. **启动与对账自动自愈修复（Item A5）**：
   - 在 App 或悬浮球后台引擎启动及 `_loadAndReconcile` 时，自动扫描所有批次，找出「所有项均已保存（`saved=true` / `JobState.done` / `mediaId != null`）但尚未结算或未写历史记录」的受阻批次。
   - 补做结算并写入文件行（使用已有的相册媒体编号 MediaStore mediaId），记录日志 `settle_repair batch=<id> files=<n>`。
   - 覆盖并自动修复真机已有受阻批次：X 帖子 `2122697609731260512`（媒体编号 `79003`）与小红书帖子 `6aff266b000000001802b822`（媒体编号 `79007–79010`），重启后自动出现在历史记录与「最近保存」中。
5. **删除确认框优化（Item B1）**：
   - 当历史记录无文件（0 项）时，删除确认弹窗不显示「0 项」（`summary=0 项`），仅显示删除记录的说明文案，且不显示「同时从系统相册中删除」勾选框；删除提示中避免显示「未能在相册中找到这 0 项」。

#### v1.12 的教训（架构复盘补充）
- **断点必须以物理落盘为准**：续传起点只能来自磁盘上的实际文件长度；绝不得用「只增不减」「取较大者」等内存或历史记录推测修补断点，否则在网络异常、重定向或重新从 0 下载时会导致 App 请求超前 Range，引发 CDN 拒绝或插件崩溃进入死循环。

     - 原实现中，Dart 端 `pauseBatch` 调用插件 `FileDownloader().pause(task)` 属于异步跨进程调用，Android 原生在子线程执行 pause。Dart 紧接着同步查询 `_getResumeData` 得到 null，未能在此时设置 `job.resumeTempPath`。
     - 当后续原生上报 `TaskStatus.paused` 时，`_onUpdate` 未去异步获取 `_getResumeData`，导致 `job.resumeTempPath` 依然为 null。
     - 用户点击继续时，`resumeBatch` 调用 `_calculateResumeStartByte`，因未传入 resumeData 且 `job.resumeTempPath` 为 null，App 尝试检查 `${root.path}/$subDir/$fName`，由于文件不存在，计算得到 `fileSize == 0`，进而触发了 `_clearResumeState`，**反手删除了插件内部保存的 ResumeData**！
     - 随后的 `_resumeTask` 因 ResumeData 已被删除而失败（`resumedSameTask = false`），最终 fallback 到 `_enqueueAttempt` 开启 `-r2`，日志显示 `has_resume_data=false from_bytes=0 reason=no_resume_data`，彻底从 0 重新下载。
     - 与之对比，断网任务在失败流 `_failAttempt` 中已预先通过 failure 回调将 `job.resumeTempPath = resumeData.data` 赋值，因此断网续传有路径，而首轮暂停没有。
   - **修复规则**：
     - **直接恢复同一任务**：用户点击继续时，只要该 job 存在处于 paused 状态的插件任务，直接调用插件 `resume`（同一个 taskId），跳过 preflight 检查，绝不开新一轮（保持单轮次任务不变）。
     - **临时文件以插件 ResumeData 为准**：计算 `partial_bytes` 与断点续传起点时，优先读取插件 `ResumeData` 中的文件路径与物理大小；`_safeCancelPreservingTemp` 在取消前同样查询 ResumeData 获取路径备份；原生上报 `TaskStatus.paused` 时异步拉取 ResumeData 并持久化 `resumeTempPath` 与 `resumeStartByte`。
     - **原生诊断日志**：原生插件在 `TaskStatus.paused` 时打印结构化日志 `pause_resume_data taskId=... present=yes|no required_start_byte=... temp_exists=... temp_size=...`（不记录敏感路径）。
     - **请求头白名单一致性**：确认 `MediaRequestPolicy.kAllowedRequestHeaderNames`、`MediaPolicyRedirects.PERMITTED_HEADERS` 与 `NativeMediaRequest` 均已完整包含 `range` 头，三处保持严格一致。

2. **测试覆盖要求更新（Item A3）**：
   - **强制要求**：续传相关测试必须包含首轮任务（从 enqueue 开始，首次响应为 200 的任务，不得只测已注入续传数据的任务）。
   - **build 76 测试遗漏原因**：build 76 的单元测试（`v112_build76_disk_resume_test.dart`）直接在内存构造的 `DownloadJob` 上注入了 `job.resumeTempPath` 指向预设的测试文件，跳过了首次 `_enqueueAttempt` 阶段原生插件自行命名分配 cache 临时文件的真实场景，从而掩盖了首轮任务暂停时 `job.resumeTempPath` 为 null 导致的清空 ResumeData 缺陷。
